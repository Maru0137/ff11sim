# 0006. ログイン時の同期は「一方向の初回アップロードを、アカウントで最初のログインに 1 度だけ、記録とデータを不可分に書いて行う」とする

（題は 2026-10-25 の改訂で変えた。当初の題は「ログイン時の同期は『一方向アップロード・Supabase 優先・ユーザーごと一度きり』とする」。）

## Context and Problem Statement

[ADR 0005](0005-localstorage-default-supabase-optin.md) により、未ログイン時は
localStorage、ログイン時は Supabase という 2 つの保存先が存在する。ゲストとして
データを作り込んだユーザーがログインすると、それまでのデータが画面から消えたように
見えてしまう。両者をどう突き合わせ、衝突をどう解決するかを決める必要がある。

## Decision Drivers

* ゲスト時に作ったデータがログインで失われたように見えないこと
* 既にクラウドにあるデータを壊さないこと（こちらの方が失うと痛い）
* 実装量が個人開発の範囲に収まること
* 同期処理が複数回走っても壊れないこと
* 別のブラウザ・別の端末・ブラウザのデータの消去の後に同じアカウントでログインしても、
  端末内データを再び送らないこと。再び送ると、後から送った端末内データが他の端末で保存した
  内容と競合する（2026-10-25 改訂で追加。[仕様書 0001](../specs/0001-saving-and-sync.md) の制約の節）
* 複数の端末で同時に最初のログインをしても、送るのは 1 つの端末だけであること。
  途中まで送った状態を残さないこと（2026-10-25 改訂で追加。仕様書 0001 の AC12・AC17）

## Considered Options

1. 同期しない（ログインすると別のデータ空間に切り替わる）
2. ログイン時に localStorage → Supabase の一方向アップロードを行う
    - 2.1. 衝突したら Supabase 側を優先し、ローカル側をスキップする（当初採用 → 2026-10-25 改訂で不要に）
    - 2.2. 衝突したらローカル側を優先し、Supabase 側を上書きする
    - 2.3. 衝突をユーザーに提示して選ばせる
3. 常時双方向同期する（last-write-wins やベクタークロック等）

2026-10-25 の改訂で、「1 度だけ」をどう守るかについて次の選択肢を足した。

4. 初回アップロードを行ったことをどこに記録し、いつ送るか
    - 4.1. ブラウザ側に済んだ印を置き、アカウントとブラウザの組で 1 度行う（当初採用 → 2026-10-25 改訂で 4.4 に置換）
    - 4.2. ブラウザ側の印をデータの種類ごとに分ける（grill の途中で一度決め、4.3 の検討で不要になった）
    - 4.3. 記録を持たず、アカウントのそのデータが空のときだけ送る
    - 4.4. 記録をアカウント側に置き、アカウントで最初にログインしたときに 1 度だけ送る
        - 4.4.1. 記録を書いてから送る
        - 4.4.2. 記録が無くアカウントデータが空であることの確認と、記録と全データの書き込みを 1 回の手続きで不可分に行う
5. この仕様の前にログインしたことのある、記録の無いアカウントの扱い
    - 5.1. 記録が無ければ改めて初回アップロードを行う
    - 5.2. アカウントデータが空でなければ済んだものとみなす（みなしだけに頼る）
    - 5.3. 導入時に記録を一括で書き、それでも記録が無くアカウントデータが空でなければ済んだものとみなす

## Decision Outcome

選択: **2 + 4.4 + 4.4.2 + 5.3**（当初は 2 + 2.1 + 4.1。2026-10-25 の改訂で変更）。

双方向同期（選択肢 3）は更新時刻の管理と削除の伝播が必要になり、この規模の
アプリケーションには過剰である。同期の向きは当初どおり端末内データからアカウントデータへの
一方向とし、送るのは初回アップロードだけである。

- 初回アップロードは、アカウントで最初にログインしたときに 1 度だけ、そのとき使っている
  ブラウザの端末内データをアカウントデータに加える（[仕様書 0001](../specs/0001-saving-and-sync.md)
  の用語「初回アップロード」）。
- 行ったことは **初回アップロードの記録** としてアカウント側に置く。1 つのアカウントに
  高々 1 つで、サーバー側の一意制約で 1 つに限る（仕様書 0001 の制約の節）。
  記録の置き場（専用の表かアカウントの設定の行か）は未決（仕様書 0001 の D2）。
- ログインした直後と、ログインした状態でページを開いたときに、記録が無ければ行う。
  記録があれば、どのブラウザ・端末からでも行わない（仕様書 0001 の AC11）。
- 記録が無くアカウントデータが空であることの確認と、記録と端末内データの全データの書き込みを、
  1 回の手続きで不可分に行う。手続きに成功した 1 つのブラウザだけが記録とデータを書く。
  端末内データが空でも記録を書く（仕様書 0001 の AC12）。手続きの作り方（例: サーバー側の
  1 つの関数）は未決（仕様書 0001 の D2）。
- 最初のログインの時点でアカウントデータは空なので、衝突は起きない。キャラクターと装備セットは
  ID をそのまま送り（[ADR 0005](0005-localstorage-default-supabase-optin.md)、
  [仕様書 0002](../specs/0002-character-management.md) の AC27、
  [仕様書 0006](../specs/0006-equipset-editing.md) の AC4）、並び順も端末内データのままである。
  初回アップロードはアカウントデータを書き換えも削除もせず、端末内データも変えない
  （仕様書 0001 の AC13〜AC15）。
- 手続きが失敗したら記録もデータも書かず、失敗したことを画面で知らせ、次にログインした状態で
  ページを開いたときに改めて判定する（仕様書 0001 の AC17）。
- 記録があって送らなかったとき、端末内データに 1 件以上あれば、送らなかったことを画面で知らせる。
  2 台目以降の端末の端末内データは端末内に残る（仕様書 0001 の AC18・AC56）。知らせ方は未決
  （仕様書 0001 の D1）。
- 既存のアカウントには、導入時に、アカウントデータが空かどうかによらず記録を一括で書く
  （仕様書 0001 の AC62）。それでも記録が無くアカウントデータが空でなければ、済んだものとみなして
  送らず、記録を書く。書けなかったときも送らず、次に開いたときに書き直す（仕様書 0001 の AC48）。
  一括で書く方法は未決（仕様書 0001 の D2）。
- 記録・アカウントデータ・端末内データのどれかの読み込みに失敗して判定できないときは、
  初回アップロードを行わず、読み込みの失敗の表示で知らせる。記録の読み込みに失敗したときは、
  さらにすべてのデータの種類の書き込みを止める（仕様書 0001 の AC50）。
- 初回アップロードが終わると、送った件数が 0 件でも、表示しているものをすべてアカウントデータで
  表示し直す（仕様書 0001 の AC19）。
- 認証状態の変化は、ログイン中のアカウントが変わったときだけ画面に通知し、セッションの復元や
  トークンの更新では通知しない（当初の決定から変えていない。仕様書 0001 の制約の節）。

当初の決定（2026-08-02）と、改めた理由:

- 当初は、`web/js/sync.js` が `onAuthChange` を購読してログイン検知時に `syncLocalToSupabase(user)`
  を実行し、Supabase 側の既存キー（character は `name`、equipset は `character|job|name`）を
  先に取得して **衝突しないものだけ** を insert していた（2.1）。完了後に localStorage に
  `ff11sim_synced_<user.id>` フラグを立て、同一ユーザーでは二度と同期しない（4.1）。
  同期完了時（アップロード 0 件でも）`ff11sim:synced` イベントを発火し、多重起動は
  `_syncing` フラグで抑止していた。「失って痛いのはクラウド側」という判断から、衝突時は
  クラウドを守った。衝突解決 UI（2.3）は衝突の頻度に割に合わないとして退けた。
- 4.1 を改めた理由: 済んだ印をブラウザ側に置くと、別のブラウザやブラウザのデータの消去の後に
  同じアカウントへ再び送られ、後から送った端末内データが他の端末で保存した内容と競合するため
  （仕様書 0001 の grill で決定）。最初のログインではアカウントデータが空なので、同じものの判定
  （2.1〜2.3 の衝突解決）も要らなくなった（仕様書 0002 の制約の節: 名前が等しいキャラクターが
  あればアカウントの側を優先して送らない、を却下）。
- 4.2 を採らなかった理由: 当初の実装では、後から足した同期対象（プロパティセット）を既に済んだ
  利用者にも送るため、2 組目の印（`ff11sim_synced_propsets_<user.id>`）を足していた。データの
  種類ごとの印なら同期の対象を足しても同じ問題が起きないとして一度採ったが、記録をアカウントに
  1 つ置く 4.4 では不要になった。
- 4.3 を採らなかった理由: 「端末 A がログイン中に編集し、端末 B が後からログインして初回アップロードし、
  A が保存する」と、B が送ったカスタムステータスビューが A の保存で上書きされうる。また、空かを
  確かめてから書くまでの間に競合しうる。4.4 ではどちらも起きない。4.3 には「利用者がアカウントの
  データを全部消した後にログインし直すと、端末内の古いデータが送られうる」というトレードオフもあった。
- 4.4.1 を採らなかった理由: 記録を書いてから送り終えるまでの間に別の端末が保存すると、空のはずの
  アカウントデータと衝突して送信が途中で失敗しうるため。4.4.2 なら途中まで送った状態を残さず、
  記録も書かれないので再び行っても複数の端末から送られない（仕様書 0001 の制約の節。却下案には
  「衝突した件だけ飛ばして残りを送る」も含む）。
- 5.1・5.2 を採らなかった理由: 既存のアカウントはブラウザ側の印で初回アップロードを既に済ませており、
  もう一度送ると端末内データの古い内容が加わるため。アカウントデータを全部消したアカウントでは
  アカウントデータが空になり、みなし（5.2）だけでは防げないため、導入時に一括で書く（仕様書 0001 の
  制約の節）。
- 記録の読み込みに失敗したときにすべての書き込みを止める理由: 読み込めずに壊れたデータを、間違って
  上書き保存するのを避けるため（ユーザーの理由。仕様書 0001 の制約の節。却下案: 記録はデータの
  書き込みの安全性に関係しないので、どの種類の書き込みも止めない）。

### Consequences

* Good: ゲスト時のデータが、そのアカウントで最初のログインの後も引き継がれ、消えたように見えない。
* Good: 既存のクラウドデータは決して上書きされない。初回アップロードは加えるだけである。
* Good: 初回アップロードはアカウントごとに 1 度だけで、別のブラウザ・端末・ブラウザのデータの
  消去の後にも再び走らない（2026-10-25 改訂。当初は再び走りえた）。
* Good: 最初のログインではアカウントが空なので、衝突の判定も、更新時刻や tombstone も要らない。
* Good: 手続きが不可分なので、失敗しても途中まで送った状態は残らず、再試行できる
  （2026-10-25 改訂。当初は部分的に insert 済みの状態から再開していた）。
* Good: 送らなかったことと失敗を画面で知らせる（2026-10-25 改訂。当初は `console.log` のみだった）。
* Bad: 2 台目以降の端末で作った端末内データは、アカウントへ自動では送られない。
  利用者が明示的に取り込む操作は未作成の仕様書として残っている（仕様書 0001 のスコープ外の節）。
* Bad: 同期は一方向のみ。クラウド側のデータがローカルへ降りてくることはないため、
  ログアウトすると再びローカルのデータだけが見える状態に戻る。
* Bad: 記録をアカウント側に置き、確認と書き込みを 1 回の手続きにするため、サーバー側の仕組み
  （一意制約と、不可分に書く手続き）と、既存アカウントへの一括の書き込みが要る（2026-10-25 改訂）。
* Neutral: 同期は「移行」であって「継続的な同期」ではないという位置づけ。

### Confirmation

当初の決定について確かめたこと（2026-08-02 時点の `web/js/`。その後 `web/src/*.ts` に移った）:

* `web/js/supabase-client.js` の `onAuthStateChange` は、直前のユーザー ID と
  比較して変化があったときだけリスナを呼ぶ。`INITIAL_SESSION` のリプレイによる
  重複起動を防いでいる。
* `web/js/sync.js` の `_syncing` フラグが、同期中の再入を防ぐ。
* `syncFlagKey(user.id)` によるフラグで、同一ユーザーの二重同期を防ぐ。

2026-10-25 の改訂の内容は未実装（仕様書 0001・0002・0006 の受け入れ基準と実装の差。issue 化予定）:

* `web/src/sync.ts:16-20` は、済んだ印をブラウザ側（localStorage）に 2 組置き、衝突した名前を
  飛ばして insert している。アカウント側の初回アップロードの記録と、記録と全データを 1 回の手続きで
  書く形（仕様書 0001 の AC11・AC12・AC17・AC62）になっていない。
* ID をそのまま送ること（仕様書 0002 の AC27、仕様書 0006 の AC4）。ID による識別そのものが未実装
  （[ADR 0005](0005-localstorage-default-supabase-optin.md)）。
* 送らなかったことと失敗の画面での知らせ（仕様書 0001 の AC17・AC18）、読み込みの失敗での停止
  （仕様書 0001 の AC50）。

検証されていないもの:

* 初回アップロードを検証する自動テストは存在しない。CI は `cargo test` のみを実行する
  （[ADR 0001](0001-rust-wasm-static-site.md)）。

## Pros and Cons of the Options

### 1. 同期しない

* Good: 実装が不要。データが勝手に動かないため挙動が予測しやすい。
* Bad: ゲスト時に作ったデータがログイン後に見えなくなり、消えたと受け取られる。
* Bad: ログインを試すこと自体が損失に感じられ、クラウド保存への移行を妨げる。

### 2. ログイン時に localStorage → Supabase の一方向アップロードを行う（採用）

* Good: 「ゲストからユーザーへの移行」という実際に起きる場面だけを扱えばよく、実装が小さい。
* Good: 同期の向きが 1 つなので、何が起きるかをユーザーに説明しやすい。
* Bad: クラウド側の変更がローカルへ降りてこない。ログアウトすると再びローカルのデータだけが見える。

#### 2.1. 衝突したら Supabase 側を優先し、ローカル側をスキップする（当初採用 → 2026-10-25 改訂で不要に）

* Good: 既存のクラウドデータを決して壊さない。失って痛い方を守れる。
* Good: 判定が「キーが既に存在するか」だけで済み、更新時刻の管理が要らない。
* Bad: 同名で衝突したローカルの編集内容が黙って捨てられる。
* Bad: ユーザーには何が起きたか分からない（通知が `console.log` のみ）。
* 改訂後は、最初のログインの時点でアカウントが空なので衝突が起きず、2.1〜2.3 のどれも要らない。

#### 2.2. 衝突したらローカル側を優先し、Supabase 側を上書きする

* Good: 直前まで触っていたデータが残るため、ユーザーの直感に近い場合がある。
* Bad: 別端末で作り込んだクラウドのデータを、古いローカルデータで破壊しうる。
  損失の方向が逆で、より痛い。
* Bad: 「ログインしたら別端末のデータが消えた」という最悪の体験を生む。

#### 2.3. 衝突をユーザーに提示して選ばせる

* Good: データが失われない。ユーザーが意図を持って決められる。
* Bad: 衝突解決 UI の実装コストが、実際に衝突が起きる頻度（同名のキャラクターを
  ローカルとクラウドの両方に持つ場面）に見合わない。
* Bad: ログイン直後という最も離脱しやすい場面で、ユーザーに判断を要求することになる。

### 3. 常時双方向同期する

* Good: どの端末で編集しても最新状態が共有され、ユーザーが同期を意識しなくてよい。
* Bad: 更新時刻の管理、削除の伝播 (tombstone)、競合マージが必要になり、
  実装量がこのアプリの規模に見合わない。
* Bad: 同期の不具合がそのままデータ破壊に直結する。

### 4. 記録の置き場と送る時点

#### 4.1. ブラウザ側に済んだ印を置く（当初採用 → 2026-10-25 改訂で 4.4 に置換）

* Good: サーバー側に仕組みが要らず、実装が小さい。
* Bad: 別のブラウザ・別の端末・ブラウザのデータの消去の後に、同じアカウントへ再び送られる。
  そのときローカルに古いデータが残っていれば、他の端末で保存した内容と競合する。
* Bad: 後から同期の対象を足すと、既に済んだ利用者に送るための印を足す必要がある
  （実際に `ff11sim_synced_propsets_<user.id>` を足した）。

#### 4.2. ブラウザ側の印をデータの種類ごとに分ける

* Good: 同期の対象を足しても、既に済んだ利用者にその種類だけを送れる。
* Bad: ブラウザ側に置く問題（4.1 の 1 つ目の Bad）は残る。

#### 4.3. 記録を持たず、アカウントのデータが空のときだけ送る

* Good: 記録が要らない。
* Bad: 他の端末がログイン中に保存すると、後から送った内容が上書きされうる。空かを確かめてから
  書くまでの間に競合しうる。
* Bad: アカウントのデータを全部消した後にログインし直すと、端末内の古いデータが送られうる。

#### 4.4. 記録をアカウント側に置き、最初のログインで 1 度だけ送る（採用）

* Good: 「1 度だけ」の単位がアカウントになり、どのブラウザ・端末からでも再び走らない。
* Good: 最初のログインではアカウントが空なので、衝突も同じものの判定も起きない。
* Bad: サーバー側に記録の置き場と一意制約が要る。

##### 4.4.1. 記録を書いてから送る

* Good: 確認と書き込みを 1 つの手続きにまとめなくてよい。
* Bad: 記録を書いてから送り終えるまでに別の端末が保存すると、送信が途中で失敗しうる。
  失敗しても再び行わないので、途中まで送った状態が残る。

##### 4.4.2. 確認と、記録と全データの書き込みを不可分に行う（採用）

* Good: 途中まで書かれた状態が残らず、失敗しても次に改めて行える。
* Good: 複数の端末で同時に始まっても、手続きに成功した 1 つだけが書く。
* Bad: サーバー側に不可分に書く手続きが要る。

### 5. 記録の無い既存アカウントの扱い

#### 5.1. 記録が無ければ改めて初回アップロードを行う

* Bad: 既にブラウザ側の印で済ませたアカウントへ、端末内データの古い内容が再び加わる。

#### 5.2. みなしだけに頼る

* Good: 導入時の一括の書き込みが要らない。
* Bad: アカウントデータを全部消したアカウントでは空になり、みなしが成り立たず再び送られる。

#### 5.3. 導入時に一括で書き、みなしも併用する（採用）

* Good: 既存アカウントで再び送られることを防ぎ、一括で書き漏れたアカウントもみなしで防ぐ。
* Bad: 導入時に既存アカウントへ記録を書く移行が要る。
