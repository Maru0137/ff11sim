# 0020. 未保存の編集を共通ガードで確認し、保存ボタンは編集時のみ有効にする

## Context and Problem Statement

装備セット編集フォームとキャラクター編集フォームは、編集の有無に関係なく保存ボタンが
常に押せる状態で、かつ編集を捨てる操作（装備セットのタブ切替、キャラ/ジョブセレクタの
変更、キャラクターの別レコードを開く、ログアウト、リロード）が無言で実行されていた。
「編集したときだけ保存ボタンを有効にし、編集内容が失われる操作には確認を出す」ために、
(a) 編集有無の判定方式、(b) 確認ダイアログの選択肢、(c) ガードを掛ける操作の範囲、
(d) 保存済み内容が前提の操作（複製・共有）の扱い、(e) ログイン同期による再読込の扱い
を決める必要がある。

## Decision Drivers

* 編集した値を元に戻したら「未編集」に戻ること（保存ボタンが押せるままだと嘘になる）
* 確認ダイアログを出す操作は、実際にデータが失われる操作だけであること
  （失われない操作で警告すると説明が事実と食い違い、「破棄」がむしろ害になる）
* 編集フォームは装備セット / キャラクターの 2 つがあり、今後増えても同じ規則で扱えること
* 装備セットの状態は React の外（`equipState` の可変オブジェクト）にあり、
  キャラクターフォームは React の `useState` にある — 判定方式を片方に寄せられないこと
* 「破棄して続行」の後に古い編集が残って、無関係な操作でダイアログが再発しないこと

## Considered Options

1. 編集有無（dirty）の判定方式
    - 1.1. 変更イベントで立てるフラグ
    - 1.2. 読み込み / 保存時のスナップショットと現在値の比較
2. 確認ダイアログの選択肢
    - 2.1. ブラウザ標準 `confirm`（続行 / キャンセルの 2 択）
    - 2.2. 2 択（破棄して続行 / キャンセル）の自前モーダル
    - 2.3. 3 択（保存して続行 / 破棄して続行 / キャンセル）の自前モーダル
3. ガードの実装位置
    - 3.1. 各画面がそれぞれ確認処理を持つ
    - 3.2. 共通レジストリ（DirtyEditor の登録）+ `guard()` に一元化
4. 複製・共有（保存済み内容が対象の操作）の扱い
    - 4.1. ガードを掛けて「保存して続行 / 破棄して続行」を選ばせる
    - 4.2. 未保存の間はボタンを無効化する
5. ログイン同期による再読込（`refreshEquipSetPanel`）の扱い
    - 5.1. 再読込処理の入口でガードする
    - 5.2. ログアウト操作をガードし、ログインは `beforeunload` に任せる

## Decision Outcome

選択: **1.2 + 2.3 + 3.2 + 4.2 + 5.2**。

- `web/src/dirty-guard.ts` に `DirtyEditor`（`label` / `isDirty` / `save` / `discard`）の
  レジストリと `guard(action, proceed, options)` を置く。編集内容が失われる操作は
  すべて `guard()` を通し、未保存なら `UnsavedChangesModal` を出して
  「保存して続行 / 破棄して続行 / キャンセル」を選ばせる。
- `save()` は `true | string` を返す（失敗理由を文字列で返す）。名前未入力・名前重複で
  保存できないときはダイアログを閉じずに理由を表示し、移動もしない。
  この規約に合わせて `saveEquipSet` / キャラクターの `save` は `alert` を返り値へ置き換え、
  ボタンから直接押されたときだけ呼び出し側が `alert` する。
- 「破棄して続行」は `proceed()` の前に `discard()` を呼ぶ。破棄したのに dirty が残ると、
  移動先で無関係な操作をしたときにダイアログが再発するため。
  装備セットの `discard()` は保存済みレコードの複製（`structuredClone`）を読み直す
  — スロットの値オブジェクトは装備選択モーダルが直接書き換えるので、控えは複製で持つ。
  キャラクターの `discard()` はフォームを閉じる。
- ガード対象は「実際に編集が失われる操作」に限る:
  装備セットのタブ切替 / 新規 (+) / タブの並べ替え / キャラ・ジョブセレクタの変更、
  キャラクターの別レコードを開く / 新規 / フォームを閉じる、ログアウト、ページ離脱
  （`beforeunload`）。
  サイドバーのビュー切替は対象外 — 3 ビューは `display:none` で切り替えるだけで
  アンマウントされない（App.tsx）ため編集は失われない。
  サポートジョブの選択は装備セットレコードに保存されないため対象外。
  削除は既存の `confirm` に任せる（対象そのものを消す操作で、編集の消失は自明）。
- 保存ボタンは未編集なら無効。複製・共有は保存済み内容に対する操作なので、
  未保存の間は無効にする。特に複製は編集中の `currentEquipSlots` からコピーを作って
  複製元の編集を捨てる挙動だったため、無効化でこの不整合ごと解消する。
- キャラクターフォームの「キャンセル」は「閉じる」に改名し中立色
  （`.btn-neutral`）にする。装備セット側と違いフォームを閉じる手段が他に無いので
  ボタン自体は残すが、役割は破棄ではなくクローズであり、未保存ならガードが確認する。
- セレクタ（controlled な `<select>`）のガードでは、キャンセル時に
  `notifyEquipState()` で再描画させる。state が変わらないと React は再描画せず、
  DOM だけユーザーが選んだ値のまま残るため。

### Consequences

* Good: 値を元に戻せば未保存表示も保存ボタンも自動的に戻る（フラグ方式の消し忘れが無い）。
* Good: 編集フォームを増やすときは `DirtyEditor` を 1 つ登録するだけで、
  ガード対象の操作側は変更不要。
* Good: 「保存して続行」で移動をやめずに保存でき、保存できないときは理由が出たまま留まる。
* Bad: dirty 判定が毎レンダーの JSON 比較になる（装備 16 スロット + キャラクターフォーム全体）。
  実測で問題になる規模ではないが、比較対象を増やすとレンダーごとのコストが増える。
* Bad: 装備セット側は「保存対象のフィールド」を `equip-set-snapshot.ts` で明示的に
  列挙しているため、保存レコードに項目を足したらスナップショットにも足す必要がある。
* Bad: ログインは OAuth リダイレクトで離脱するため、確認はブラウザ標準の
  `beforeunload` ダイアログになり、文言を制御できない。
* Neutral: ビュー切替をガードしないので、「装備検索で調べてから戻る」動線は無警告のまま
  維持される（編集も維持される）。

### Confirmation

* `web/src/dirty-guard.test.ts`: 未編集なら確認せず実行 / 未保存ならダイアログを開いて操作を保留 /
  `editorId` 指定時に他エディタの未保存を無視 / 登録解除で判定から外れる /
  保存成功で続行・保存失敗（返り値・例外の両方）で移動しない /
  破棄で `discard()` を呼んでから続行 / キャンセルで `onCancel` のみ呼ぶ、を検証。
* `web/src/equip/equip-set-snapshot.test.ts`: スロットのキー順・`null`/`undefined`/欠落の差を
  変更とみなさないこと、表示用フィールド（`name_ja` 等）の差を無視すること、
  装備・オーグメント・カスタム説明・名前・プロパティセット選択の変更を検出すること、
  元に戻せば一致することを検証。
* `tests/smoke.spec.js`「未保存の変更で保存ボタンが有効化され、タブ切替が確認ダイアログを挟む」:
  ストア 2 つ（`equipSetsStore` / `equipState`）の通知がツールバーへ届く配線を含めて、
  保存ボタンの活性・複製の無効化・未保存マーク・キャンセルで留まる・破棄で持ち越さない、
  をブラウザ上で確認する。
* `tests/smoke.spec.js` の既存 13 件（装備セットの保存、プロパティセット選択の記憶、
  共有 URL 閲覧など）が引き続き通ることで、保存経路と共有閲覧モードへの影響が無いことを確認する。

## Pros and Cons of the Options

### 1.1. 変更イベントでフラグを立てる

* Good: 判定が O(1) で実装も最小
* Bad: 値を元に戻しても未保存のままになり、保存ボタンが押せる状態が残る
* Bad: 変更経路（スロット選択モーダル・オーグメント・カスタム説明・プロパティセット選択）
  ごとにフラグ立てを足す必要があり、追加漏れが静かに起きる

### 1.2. スナップショット比較（採用）

* Good: 変更経路を知らなくてよい。判定は「今の値」だけを見る
* Good: 元に戻せば未保存でなくなる
* Bad: 比較のたびに JSON 化のコストがかかる
* Bad: 何を比較対象にするかを明示的に決める必要がある（表示用フィールドを含めると
  同じ装備の再選択が変更として出る）

### 2.1. ブラウザ標準 `confirm`

* Good: 実装が要らない
* Bad: 「保存して続行」を出せず、保存したいユーザーは一度キャンセルして保存し直す必要がある
* Bad: 文言・ボタンラベルを制御できない

### 2.2. 2 択の自前モーダル

* Good: 実装が単純で、選択肢が少なく迷わない
* Bad: 「保存し忘れ」が主因なのに、その場で保存できない

### 2.3. 3 択の自前モーダル（採用）

* Good: 保存し忘れをその場で解決でき、往復が要らない
* Bad: 保存できない状態（名前未入力・重複）を扱う必要があり、
  ダイアログ内にエラー表示と「留まる」分岐が要る

### 3.1. 各画面が個別に確認処理を持つ

* Good: 画面ごとに文言や選択肢を自由にできる
* Bad: 確認を通す操作が増えるたびにコピーが増え、抜けが出る
* Bad: `beforeunload` やログアウトのような「どの画面が未保存かを知りたい」処理から
  横断的に問い合わせられない

### 3.2. 共通レジストリ + `guard()`（採用）

* Good: 「編集が失われる操作は `guard()` を通す」という 1 つの規則で済む
* Good: `isAnyDirty()` で画面をまたいだ判定ができ、`beforeunload` が 1 箇所で書ける
* Bad: エディタの `save` / `discard` を後から差し替える必要があり、
  React 側では ref 経由の登録という一手間が要る

### 4.1. 複製・共有もガードする

* Good: 操作を止めない（未保存でも先に進める）
* Bad: 複製は「編集中の内容でコピーを作り、複製元の編集は捨てる」挙動なので、
  ダイアログで説明しきれない結果になる
* Bad: 共有は保存済み内容を共有するため、画面と共有結果が食い違ったままになりうる

### 4.2. 未保存の間は無効化する（採用）

* Good: 押せた時点で「画面の内容 = 保存済みの内容」が保証され、上記の食い違いが消える
* Good: 実装が単純（ガードの分岐が増えない）
* Bad: 複製したいだけでも先に保存が必要になる

### 5.1. 再読込処理の入口でガードする

* Good: 再読込でデータが入れ替わる箇所を直接押さえられる
* Bad: 再読込が走るのは実質ログイン完了後（`onAuthChange` / `ff11sim:synced`）で、
  その時点ではログインは終わっておりユーザーに取れる手が無い。
  しかもログインは OAuth リダイレクトでページを離れるため、
  戻ってきた時点で編集内容はそもそも存在しない
* Bad: `refreshEquipSetPanel` は起動時初期化からも呼ばれ、ガードの対象を選り分ける条件が要る

### 5.2. ログアウト操作をガードし、ログインは `beforeunload` に任せる（採用）

* Good: ダイアログの 3 択がすべて意味を持つ（保存してログアウト / 破棄してログアウト /
  ログアウトしない）
* Good: 認証リスナはユーザー ID が変わったときだけ発火する（`supabase-client.ts`）ため、
  トークン更新やタブ復帰で誤発火しない
* Bad: ログイン時の確認はブラウザ標準文言になる
* Neutral: リアルタイム購読やポーリングは無く、他端末の変更が勝手に降ってくることはないため、
  外部要因の再読込はこの 2 経路以外に存在しない
