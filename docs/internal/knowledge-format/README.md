# ナレッジの書き方

[docs/internal/knowledge/](../knowledge/) には、FINAL FANTASY XI のゲームの概念や仕様を説明する文書を置く。
1 本の文書は 1 つの概念（防御力、スマイト、メリットポイントなど）を説明し、計算式はその説明の一部として書く。
後から内容の妥当性を確かめられるよう、主張ごとに出典をたどれる形で書く。

このディレクトリはその書き方を定める。この文書はすべてのナレッジに共通の規則を、ほかの文書は分類（frontmatter の `type`）ごとの本文の形を定める。
分類とナレッジのディレクトリは 1 対 1 に対応する。書き方の文書は分類ごとに 1 本置くが、同じ形で書く文書がほかに無い分類（アイテム）には置かず、共通の規則だけに従う。分類名はナレッジの置き場の名前で、[用語集](../../../CONTEXT.md) の語とは別物である。分類名が指すゲームの概念（ジョブ特性など）の定義は、その分類のディレクトリの上位概念の文書（「上位概念の文書」節）にある。

| 分類（`type`） | ナレッジのディレクトリ | 書き方 |
|---|---|---|
| ステータス | `status/` | [status.md](status.md) |
| ジョブ特性 | `job_traits/` | [job_traits.md](job_traits.md) |
| ジョブアビリティ | `job_abilities/` | [job_abilities.md](job_abilities.md) |
| アイテム | `items/` | 無し（共通の規則だけに従う） |
| 育成 | `growth/` | [growth.md](growth.md) |
| ゲームシステム | `game_system/` | [game_system.md](game_system.md) |
| TIPS | `tips/` | まだ無い。最初の文書を書くときに作る |

## OKF に従う

`docs/internal/knowledge/` は、OKF（Open Knowledge Format）v0.2 のバンドルとして書く。OKF は、YAML の frontmatter
付きの Markdown ファイルを並べたディレクトリで知識を表す形式で、仕様は
[okf/SPEC.md](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/62432a0/okf/SPEC.md) にある。
バンドルはその配布単位のディレクトリ、コンセプトはバンドルの中の Markdown ファイル 1 本を指す。

OKF の規則のうち、このバンドルで守るのは次の点である。

- `index.md` と `log.md` 以外の `.md` はすべてコンセプトで、frontmatter を持つ（SPEC §3.1、§11）。
  そのため、このディレクトリのようなバンドルについての説明はバンドルの外に置く。
- バンドルの root に `index.md` を置き、frontmatter に `okf_version: "0.2"`、本文にすべてのコンセプトの一覧を書く（SPEC §8、§12）。
  コンセプトを足す・消す・`title` や `description` を変えたときは、`index.md` も直す。
- `log.md` は置かない。更新の履歴は git で追う。

OKF から外れる点は次のとおり。どれも OKF の適合条件（SPEC §11）には反しない。

- 出典は frontmatter の `sources` と脚注 `[^id]`（SPEC §5.1）ではなく、本文の番号と `## 出典` の一覧で書く（「出典」節）。
- リンクは、OKF が推奨するバンドル基準の絶対パス（`/status/attack.md`）ではなく、相対パスで書く。
  バンドルがリポジトリの部分ディレクトリなので、絶対パスは GitHub 上でリポジトリの root 基準になり、リンクが切れるため。

## 置くもの・置かないもの

ナレッジに置くのは、ゲームの振る舞いと、アイテムデータなどの外部データの性質である。ff11sim をどう作るかは置かない。

| 書きたいこと | 置き場 |
|---|---|
| ゲームの概念と仕様（計算式を含む） | `docs/internal/knowledge/` |
| ff11sim が何をどう計算・表示するか、何を計算しないか | 仕様書（`docs/internal/specs/`） |
| 設計判断とその理由 | ADR（`docs/internal/adr/`） |
| ff11sim 全体で横断的に使う語 | 用語集（ルートの `CONTEXT.md`） |
| ナレッジと実装の食い違い、ゲームにはあるが計算していないもの | tech-debt（`docs/internal/tech-debt/`） |

ff11sim が何をどう計算・表示するか、コードのどこにあるかは、ナレッジに書かない。それらは仕様書・ADR・tech-debt に書き、そこからナレッジへリンクする。
ナレッジはゲームの説明だけで読めるようにし、ff11sim の実装が変わっても書き直さずに済むようにするためである。

## 共通の形

どの `type` も次の形にする。「本文」の部分だけが分類ごとに違い、分類ごとの書き方の文書に定める。

```markdown
---
type: <分類>
title: "<タイトル>"
description: "<冒頭の定義を短く言い直した 1 文>"
status: <draft | stable>
---

# <タイトル>

<タイトル> は、（<上位概念>のうち、 / <上位概念>の 1 つで、）…である。

_種別_: … / _上位_: … / _インスタンス元_: …（「構造の行」節）

## <分類ごとに決まった節>

## 歴史（任意）

## 未確認の事項

## 出典

1. [攻撃力 - FF11用語辞典](https://wiki.ffo.jp/html/1766.html) — 有志の辞典
```

### frontmatter

| キー | 書くこと |
|---|---|
| `type` | 分類の名前（冒頭の表のどれか）。置いたディレクトリと一致させる |
| `title` | 本文の `# タイトル` と同じ文字列 |
| `description` | 冒頭の定義を短く言い直した 1 文。`index.md` の一覧にもそのまま載せる |
| `status` | `## 未確認の事項` が「なし」でなければ `draft`。「なし」なら `stable`（SPEC §5.4） |

OKF の `verified`（誰がいつ出典と照合したか、SPEC §5.2）は使わない。確認状態は `status` と `## 未確認の事項` で表す。OKF の `tags`（SPEC §4.1）も今は使わない。

### タイトルと冒頭の文

- **タイトル**: 概念の名前。概念の名前とゲームでの呼び方が違うときだけ、ゲームの語を全角の括弧で添える（例: 近接物理命中（命中））。英語名・中身の一覧・「計算仕様」などの接尾辞は付けない。
- **冒頭の文**: 用語の定義を 1 文で書く。その概念に対応する上位概念があるときは、上位概念との関係を定義の中で示す。関係の種類で書き方を分ける。

  | 関係 | 書き方 | 例 |
  |---|---|---|
  | 分類（X が上位概念をさらに分けた区分） | 「X は、<上位概念>のうち、…のことである。」 | 基本ステータスは、ステータスのうち、HP・MP と 7 つの BP を合わせた 9 項目のことである。 |
  | インスタンス（X が上位概念に属する個々のもの） | 「X は、<上位概念>の 1 つで、…である。」 | 防御力は、二次ステータスの 1 つで、被ダメージに関係する値である。 |
  | 上位概念が無い | 「X は、…のことである。」 | メリットポイントは、レベル上限に達したキャラクターをレベルアップによらずに強化するためのポイントのことである。 |

  ナレッジの分類名（「育成」「ゲームシステム」など）は文書の置き場の分け方で、上位概念ではないので、
  それだけを理由に「〜のうち」「〜の 1 つ」と書かない。
  「この文書は何を説明するか」は書かない。それは本文の節の並びで分かる。
- **上位概念の定義の置き場**: 冒頭の文で上位概念に挙げる語は、[用語集](../../../CONTEXT.md)（ff11sim 全体で横断的に使う語）か、
  ナレッジの上位概念の文書（「上位概念の文書」節）で定義されていなければならない。上位概念の語には、その定義へのリンクを張る。
  ゲームの細かい概念（ジョブ特性・スマイト・防御力など）の定義は用語集に書かず、ナレッジに書く。

### 構造の行

冒頭の文の直後に、その概念がほかの概念とどう関係するかを、1 行に 1 項目で書く。語の構造の考え方と行の書式は、
用語集の書式（`glossary` スキルの CONTEXT-FORMAT.md）に合わせる。値に書く語は、用語集の語かナレッジで定義した語にする。

| 行 | 値 | 意味 |
|---|---|---|
| `_種別_` | `kind` / `subkind` / `role` / `phase` / `relator` / `event` / `value` のどれか | 概念の種類。`kind` はインスタンスの種類として最上位のもの、`subkind` は kind の下位でインスタンスがずっとそれのままのもの、`value` は同一性を持たず値で比べるもの。概念が型（インスタンスの集まり）のときに書く |
| `_上位_` | 語 | この概念のインスタンスは、すべて上位の語のインスタンスでもある（is-a。gUFO の specialization）。冒頭の文が「〜のうち」のときに書く |
| `_インスタンス元_` | 語 | この概念は、その語（型）のインスタンスの 1 つである（gUFO の instantiation、`rdf:type`）。冒頭の文が「〜の 1 つ」のときに書く。英語のラベルは `_Instance-of_` |
| `_インスタンス_` | 語 | この概念（型）のインスタンスのうち、ナレッジがあるもの。網羅しなくてよい。上位概念の文書に書く。英語のラベルは `_Instances_` |
| `_分割_` | 下位の語 | 並べた下位の語は互いに排他で、合わせるとこの概念全体になる |
| `_排他な下位_` | 下位の語 | 並べた下位の語は互いに重ならない（合わせてこの概念全体になるとは限らない） |
| `_排他_` | 語 | この概念と重ならない語 |
| `_重なりうる_` | 語 | この概念と重なりうる語 |
| `_使わない_` | 語 | 同じ概念を指すが使わない語 |

`_インスタンス元_` と `_インスタンス_` は、用語集の書式（glossary スキル）にも ontology スキルにも無い、ナレッジ独自の行である。
型の特殊化（`_上位_`）とインスタンス化（`_インスタンス元_`）を別の関係として扱う考え方は、UFO の OWL 実装である
[gUFO](https://nemo-ufes.github.io/gufo/) に従う。用語集の書式が「実例」と呼ぶものは、ここでいうインスタンスと同じである。

書いていない関係は「未定」であって、否定ではない（例: `_排他_` を書いていない 2 つの語は、重なるかどうかが決まっていない）。
冒頭の文と構造の行が食い違ったら、どちらかを直す。

### 上位概念の文書

分類のディレクトリには、その分類のインスタンスをまとめる上位概念の文書を 1 本置く（例: `job_traits/job_trait.md` は「ジョブ特性」、
`status/status.md` は「ステータス」）。インスタンスの文書の冒頭の「〜の 1 つ」は、この文書へリンクし、構造の行は `_インスタンス元_` にする。
上位概念の文書の本文は、分類ごとの書き方ではなく、次の 2 つの節にする。

| 節 | 書くこと |
|---|---|
| `## 一覧` | インスタンスのうちナレッジがあるものと、その文書へのリンクの表。構造の行の `_インスタンス_` と一致させる |
| `## 共通の規則` | すべてのインスタンスに共通の規則（例: ジョブ特性はメインジョブとサポートジョブのランクの大きい方を使う） |

上位概念の文書が、インスタンスではなく下位の型に分かれるとき（例: `status/status.md` は基本ステータスと二次ステータスに分かれる）は、`## 一覧` に下位の型を並べ、構造の行の `_分割_` と一致させる。
分類の中に、さらにインスタンスをまとめる型があるとき（例: ステータスの中の「二次ステータス」、二次ステータスの中の「物理命中」「物理攻撃力」）も、その型の文書を同じ形で書く。


### 本文の節

本文には、分類ごとの書き方の文書が決めた `##` を、決めた順にすべて置く。

- 必須の節に書くことが無いと確かめたときは、節を消さずに「なし」と書く。
- まだ調べていない節は置かず、「未確認の事項」に「〜は調べていない」と書く。
- 概念の説明にほかの節が要るときは、必須の節の後に `##` を足してよい。
- バージョンアップでの変更は、任意の `## 歴史` に日付ごとに書く。出典の内容が古くなっていないかを判断する材料になる。

### 見出しの名前

他の文書から「〇〇」節として参照されている見出しは、階層が変わっても名前は変えない。名前を変えるときは参照元も直す。

### 末尾の節

本文（と `## 歴史`）の後に、次の 2 つをこの順に置く。

| 節 | 書くこと |
|---|---|
| `## 未確認の事項` | 照合できていない主張。無ければ「なし」と書く（「未確認の事項」節） |
| `## 出典` | 番号付きの一覧（「出典」節） |

## 出典

本文の主張の末尾に `[1]` のように番号を付け、末尾の `## 出典` に同じ番号で一覧を置く。

- 1 つの主張が複数の出典に基づくときは `[1][2]` と並べる。
- 一覧の各項目は「リンクかタイトル（日付）— 種別」の形で書く。日付は、出典に書かれた日付か、出典を確かめた日付。
- 番号は本文に初めて出る順に振る。出典を足したり消したりしたら振り直す。
- 出典を持たない主張を本文に残すときは、番号を付けず、「未確認の事項」にその主張を挙げる。

### 出典の種別

| 種別 | 意味 | 例 |
|---|---|---|
| 公式 | スクウェア・エニックスが出した資料 | バージョンアップ情報、公式フォーラムの開発者の投稿 |
| 有志の辞典 | 有志が運営する wiki・辞典 | [FF11用語辞典](https://wiki.ffo.jp/)、[BG Wiki](https://www.bg-wiki.com/) |
| 有志の検証 | 個人が実測・解析して公開した結果 | X（旧 Twitter）の検証スレッド、ブログ |
| データの集計 | アイテムデータなどの外部データを数えた・調べた結果 | `build/items.json` を数えた件数 |
| ユーザーの確認 | ユーザーがゲーム内で確かめた結果 | ユーザーの言葉をそのまま引用する |
| ユーザーの判断 | ゲームでは確かめず、ユーザーが決めた扱い | 仕様書の grill で決めた規則 |

「ユーザーの判断」に基づく主張は、ゲームの一次情報で確かめていないので、必ず「未確認の事項」にも書く。

## 未確認の事項

照合できていない主張を箇条書きにする。何を何と照合していないかを書く。

- 良い例: 「rank4・rank5 の内部値は [1] だけに基づき、ほかの出典と照合していない。」
- 悪い例: 「一部未確認。」（どの主張か分からない）

## 文体

読者が読み返さずに論理を追えることを優先する。

- 体言止めと箇条書きだけで済ませず、主語と述語のある文で書く。
- 比較を含む語（「異なり」「大きい」など）では、何と何を比べたかを書く。
- 新しい語や略語（ジョブの略称、JP など）は初出で定義するか、[用語集](../../../CONTEXT.md) の語を使う。

## ファイルの置き場

ナレッジは、分類と同じ名前のディレクトリ（冒頭の表）に置く。新しい分類を足すときは、冒頭の表・書き方の文書・`index.md` の節を足す。
