# 0016. ステータス / プロパティ値のソース別内訳をモーダル表示する

## Context and Problem Statement

装備編集画面のステータス値・プロパティセット値（[ADR 0015](0015-property-sets.md)）は
合計値しか表示されず、合計の検算や寄与元の確認ができなかった。行 = 寄与元
（装備 16 部位 / 種族 / メインジョブ / サポートジョブ / メリポ / JP / ギフト / ML）、
列 = 項目の内訳テーブルを「内訳」ボタン → モーダルで表示するにあたり、
(a) キャラ由来の寄与値の算出方式、(b) どの寄与元にも帰属できない項
（防御の VIT×1.5 + Lv + α、魔防の基準値 100 など）の扱い、(c) 小数を持つ
基本ステータス（種族/メイン/サポは合算後に切り捨て）の表示、(d) WASM が返す
内訳データの形、を決める必要がある。

## Decision Drivers

* 内訳と合計値の計算が将来乖離（二重集計ドリフト）しないこと — 片方だけ修正される事故が最も怖い
* 検算用途なので、表の各列が「なぜその合計になるか」を正直に説明すること
* 装備の解釈は Rust 側に置く方針（[ADR 0010](0010-equipment-interpretation-in-rust.md)）と整合すること
* StatusResult の全項目（約 150）を分解する必要はなく、UI に出る列だけ賄えばよいこと
* ジョブ特性のメイン/サポ採用（絶対値の大きい方）は実計算と同一ロジックで振り分けること

## Considered Options

1. キャラ由来の寄与値の算出方式
    - 1.1. JS 側の差分法（profile からメリポ/ML 等を 1 要素ずつ抜いて再計算し差を取る）
    - 1.2. Rust に内訳 API を追加し、既存の集計関数を分解版への委譲にリファクタする
2. 帰属できない項（レベル・ステータス・スキル由来）の扱い
    - 2.1. 剰余方式: 基礎 = 合計 −（装備 + 既知のキャラ行）
    - 2.2. 「基礎」行を解析的に計算し、Σ行 == 合計の恒等式はテストで担保する
3. 基本ステータスの小数（種族 D の STR 37.5、サポは 0.25 刻み）の表示
    - 3.1. 逐次切り捨てで整数に配分する（列を足すと必ず合計に一致）
    - 3.2. 小数のまま表示し、「合算後に切り捨て」の脚注を付ける
4. WASM が返す内訳データの形
    - 4.1. ソースごとの固定 struct（StatusResult のサブセットを 7 レコード分）
    - 4.2. 疎マップ `rows: ソース → 列キー → 値`（列キーは UI と 1:1、0 は含まない）
5. スキル値列（有効スキル値と武器のスキル値）のキャラクター由来の寄与の分け方
   （2026-08-13 のスキル値列の追加で決め、2026-10-25 の改訂で選択肢として切り出した）
    - 5.1. キャップを 素 → +メリポ → +ML の順に広げ、各段の表示値の増分をその段の行に帰属させる
    - 5.2. 基礎 = スキル値とマスターレベル 0 のスキル上限の小さい方、ML = スキル上限をマスターレベル込みに
      広げたときの増分、メリポ = スキルのメリットポイントの分（スキル上限で抑えない）、ギフト = ギフトのスキルボーナス

## Decision Outcome

選択: **1.2 + 2.2 + 3.2 + 4.2 + 5.2**
（5 は当初 5.1 を採用。2026-10-25 の改訂で 5.2 に変更。理由は改訂の注記を参照）。

- `Chara::status()` / `job_trait_total()` を `status_parts()` / `job_trait_breakdown()`
  への委譲に書き換え、武器スキル解決も `combat_skills` として抽出して
  `chara_to_status_result` と内訳 (`breakdown::chara_breakdown`) で共有する。
  集計ロジックの実体は常に 1 箇所。
- 「基礎」行は `calc_defense(vit, lv, 0)` のように装備項 0 で解析的に計算する。
  剰余は使わない（帰属ミスを黙って吸収し、検算が検証にならないため）。
- 内訳の対象列は「ステータステーブルの項目 + カタログの charKey 参照項目」に限定。
  gift の `physical_attack` → 列キー `attack` のような写像は Rust 側で行い、
  JS には UI の列と 1:1 のキーだけを見せる。
- カタログ（[ADR 0015](0015-property-sets.md)）の各項目に `breakdown` メタ
  (`equipKey` / `charKey`) を追加。メタなし = 内訳非対応として列から除外し、
  非対応は `BREAKDOWN_UNSUPPORTED_IDS` に明示する（実効魔命などのスロット依存合成値）。
- スキル値列（同日改訂で対応）: breakdown メタに `skillKey`（魔法スキル: 固定キー）/
  `weaponSlot`（武器スキル: スキル種別は装備中の武器から実行時解決）を追加。
  装備行は `calculateEquipSetBonuses` の `per_slot_skill_bonuses`（全スロット別
  スキルボーナス）から引く。キャラ由来行は Rust の `skill_<Key>` / `main_weapon_skill`
  等の列で、`effective_skill_parts` により分解する。`effective_skill` は分解版への委譲。
  - 武器のスキル値の列の装備行（2026-10-25 改訂）: 全スロット共通のスキルボーナスは、
    それを持つ装備を着けたスロットの行に出す。スロット専用のスキルボーナスは、足し先が
    その列のスロットであるものだけを、それを持つ装備を着けたスロットの行に出し、足し先が
    他のスロットであるものは 0 とする（[仕様書 0007](../specs/0007-status-calculation.md) の
    AC23・AC37。振り分けの規則そのものは [ADR 0018](0018-equip-module-owns-interpretation.md)）。
    例: レンジスロットが空で矢弾スロットにアイテムレベル装備の手裏剣を着けているとき、
    その投てきスキルのボーナスはレンジスロットの武器のスキル値の列でだけ矢弾スロットの行に出る。
    元の決定は「武器スキル列では他の武器スロットの武器スキルボーナスを除外する
    （equip-bonuses のバケツ分けと同一規則）」だった。
  - キャラ由来行の分け方（2026-10-25 改訂で 5.1 → 5.2）: 基礎 = キャラクターのスキル値と
    マスターレベルを 0 としたスキル上限の小さい方 / ML = キャラクターのスキル値とスキル上限の
    小さい方から基礎を引いた増分 / メリポ = スキルのメリットポイントの分（1 ランクにつき 2。
    スキル上限で抑えない）/ ギフト = ギフトのスキルボーナス
    （[仕様書 0007](../specs/0007-status-calculation.md) の AC35。スキル上限はメリットポイントで
    広がらない。同 AC22）。ギフト行は魔法系の列だけでなく武器のスキル値の列にも出す
    （同 用語「武器のスキル値」。今は武器スキルのギフトボーナスが無いので値は変わらない）。
    元の決定（5.1）は「メリポ・ML はキャップ引き上げのため、寄与は『キャップを 素 → +メリポ →
    +ML の順に広げたときの表示値の増分』として帰属。キャラ値がキャップに届いていない分は 0。
    ギフト行は魔法系だけ」だった。
  - 列の値が '-' になる場合（2026-10-25 改訂）: 武器のスキル値が求まらないとき
    （サブスロットに `skill` が武器スキルを表す武器が無い、遠隔攻撃に使う武器が無いか楽器・風水鈴。
    [仕様書 0007](../specs/0007-status-calculation.md) の AC26・AC36）だけ、その列のすべての行の寄与を
    0 とする。メインスロットに武器が無いときは格闘として求める（同 AC26）。
    メインジョブとサポートジョブのどちらもそのスキルを持たないときも '-' にせず、
    スキル上限 0 として基礎・ML は 0、メリポ・装備・ギフトの行は出す（同 AC21・AC26）。
    元の決定は「表示値が '-'（ジョブ未習得 / 武器未装備）の列は装備ボーナスも適用されないため
    装備行も抑制する」だった。
  - 内訳モーダルのスキル値の列の帰属の注記は、上の分け方を説明する
    （[仕様書 0008](../specs/0008-status-display.md) の AC33）。
- 装備 16 部位の行は、装備セットのスロット別の値（`per_slot_stats` / `per_slot_skill_bonuses`）を
  そのまま使う。抽出は元からスロット単位なので、内訳のための計算は足さない。この値は Rust の
  `EquipSet::bonuses`（`rust/src/equip.rs`）が求め、WASM の `equip_set_bonuses` を通して
  JS の `calculateEquipSetBonuses` が返す（[ADR 0018](0018-equip-module-owns-interpretation.md) 以降。
  当初は JS 側で完結していた）。
- モーダルの合計行はパネル表示値（`StatusView.values` / `propertyValues`）を
  そのまま参照し、内訳の合計とパネル表示の定義齟齬を構造的に防ぐ。
  内訳の計算はモーダルを開いた時に遅延実行する。開いている間に計算の入力が変わったときは
  求め直す（2026-10-25 追記。[仕様書 0007](../specs/0007-status-calculation.md) の AC28、
  [仕様書 0008](../specs/0008-status-display.md) の AC38）。

**常時表示ビューの 5 列との関係**（2026-10-25 追記）

常時表示ビューの表は「素・BP からの換算・スキルからの換算・装備・合計」の 5 列にすると決めた
（[仕様書 0007](../specs/0007-status-calculation.md) の用語「素・BP からの換算・スキルからの換算・装備・合計」、
AC12〜AC14。元は「素・装備・合計」の 3 列）。5 列は 1 つのプロパティの値を**換算元ごと**に分けたもので、
内訳は**寄与元ごと**に分けたもの。同じ値を別の軸で分けているので、内訳の行は変えない
（寄与元 24 個のまま。同 AC27、[仕様書 0008](../specs/0008-status-display.md) の AC27）。

仕様書の定義から、防御力・回避・魔防・魔回避では次の対応が成り立つ
（仕様書の用語から導いた関係で、仕様書に直接は書かれていない）。

- 「装備」 = 16 スロットの行の和。スロットの寄与は装備から拾ったそのプロパティの値だけで
  （0007 AC29）、装備で上がった BP・スキル値を経由する分を含まない
- 「素」+「BP からの換算」+「スキルからの換算」 = キャラクター由来 8 行の和
- 「BP からの換算」と「スキルからの換算」は、装備の分を含む BP・有効スキル値から求める（0007 の同用語）。
  そのため装備で VIT が上がったときの防御力の増分は、スロットの行ではなく「基礎」行に入る。
  「基礎」行は「BP からの換算」「スキルからの換算」と、「素」のうちレベルや定数（魔防の 100）から
  求まる項の和にあたり、ジョブ特性・ギフト・ジョブポイントの分は「素」に入るが「基礎」行には入らない

今の実装の「基礎」行（`calc_defense(vit, lv, 0)` の `vit` は装備込みの値）は、この対応と食い違わない。

### Consequences

* Good: 内訳と合計が同じ関数（status_parts / job_trait_breakdown / combat_skills）から
  出るため、計算式の変更が自動的に両方へ反映される。
* Good: 基礎行が解析値なので、新しい寄与源の追加漏れは恒等式テストの失敗として顕在化する。
* Good: 小数表示はゲーム仕様（0.5/0.25 刻み → 合算後切り捨て）に忠実で、情報が失われない。
* Bad: `chara_to_status_result` に新しい寄与源を足すときは `chara_breakdown` にも
  同じ行を足す必要がある（両ファイルの doc コメントと恒等式テストで担保）。
* Bad: 内訳列の追加には Rust（列キー）と catalog（メタ）の両方の変更が要る。
* Neutral: 種族/メイン/サポの小数行があるため、列の単純合計と合計行は最大 0.75 ずれる
  （脚注で説明）。

### Confirmation

* `rust/src/breakdown.rs` の `mod tests`: 恒等式（基本 9 ステは
  `floor(Σキャラ行) + 装備 == StatusResult`、防御/回避/魔防/プロパティ列は
  `Σ行 + 装備 == StatusResult`、スキル値列は `Σキャラ行 == 表示スキル値`）、
  特性のメイン/サポ振り分け、メリポ/ギフトの行帰属を検証。
* `web/src/propsets/catalog.test.ts`: 全カタログ項目が `breakdown` メタを持つか
  `BREAKDOWN_UNSUPPORTED_IDS` に明示されていることを強制（新項目追加時に対応可否の判断を要求）。
* `web/src/status/breakdown.test.ts`: 列組み立て（非対応項目の除外、ユーザー定義項目、
  デスの tenacity 非適用、スキル値列の skillKey / weaponSlot メタ）と行×列モデル
  （0 → '-'、負値保持、小数保持、合計行の参照、武器スキル列の他武器スロット除外、
  表示 '-' 時の装備行抑制）を検証。
* `web/src/equip/equip-bonuses.test.ts` / `web/src/propsets/user-item-values.test.ts`:
  スロット別集計（per_slot_stats の総和一致、per_slot_skill_bonuses のスロット別保持）を
  実 WASM で検証。
* `tests/smoke.spec.js`「内訳モーダルが開ける」: JS→WASM シグネチャとテーブル描画の生存確認。

2026-10-25 の改訂分は未実装（仕様書 0007・0008 の受け入れ基準と実装の差。issue 化予定）:

* スキル値列の分け方 5.2（[仕様書 0007](../specs/0007-status-calculation.md) の AC35）。
  今の `effective_skill_parts`（`rust/src/skills.rs`）はメリットポイントでキャップを広げる 5.1 のまま。
* 武器のスキル値の列のギフト行と、スロット専用 / 全スロット共通の振り分けに従う装備行
  （0007 の AC23・AC37）。今は武器スロットの装備が持つ武器スキルのボーナスをすべてそのスロット専用として扱う。
* どちらのジョブもスキルを持たない列で '-' にせず、メリポ・装備・ギフトの行を出すこと（0007 の AC21・AC26）。
* 常時表示ビューの 5 列（0007 の AC12〜AC14、[仕様書 0008](../specs/0008-status-display.md) の AC4・AC5・AC39）。
  今の表は「素・装備・合計」の 3 列。
* 開いている間に計算の入力が変わったときの求め直し（0007 の AC28）は、実装が満たしているかを確かめていない。

## Pros and Cons of the Options

### 1.1. JS 側の差分法

* Good: Rust の変更が不要
* Bad: ギフト/JP は `total_jp_spent()` 経由でジョブ特性ランクにも効くため、
  1 要素を抜いた再計算では寄与が分離できない（BLU の特性効果アップ等）
* Bad: 再計算 7 回 + 差分の意味づけが暗黙的で、計算変更に追従できない

### 1.2. Rust 内訳 API + 委譲リファクタ（採用）

* Good: 集計の実体が 1 箇所になり、既存の数値回帰テストが委譲リファクタの
  挙動不変を証明する（f32 加算順序を保てば floor 境界も不変）
* Good: 特性の採用判定（絶対値比較、同値はメイン）を実計算と共有できる
* Bad: wasm-pack の再ビルドが必要。関数追加時は web/js/wasm.js と
  web/src/wasm.ts の再エクスポートも更新する（[ADR 0012](0012-react-ui-framework.md) の不変条件）

### 2.1. 剰余方式

* Good: 実装が最小で、表は常に合計と一致する
* Bad: ソースの帰属バグ（ギフトの入れ忘れ等）を基礎行が黙って吸収し、
  「常に一致する検算」は検証として機能しない

### 2.2. 解析的な基礎行 + 恒等式テスト（採用）

* Good: 帰属ミスがテスト失敗（またはランタイムでの合計不一致）として見える
* Bad: 基礎項の式（防御の α、回避のスキル項など）を breakdown 側にも書く必要がある
  （calc_* 関数を装備項 0 で呼ぶ形に限定して重複を最小化）

### 3.1. 整数に配分

* Good: 列の合計が常に一致して見た目が揃う
* Bad: 配分順序という恣意性が入り、実際の値（37.5 等）と 1 ずれる行が出る

### 3.2. 小数のまま表示（採用）

* Good: ゲーム仕様の実値で情報が失われない。既存テストのコメント自体が
  この表現（floor(37.50+45.00+13.50)）で書かれている
* Bad: 列の単純合計と合計行が最大 0.75 ずれ、脚注での説明が要る

### 4.1. ソースごとの固定 struct

* Good: 型が明示的
* Bad: フィールド一覧が StatusResult（約 150 項目）と将来ドリフトする。
  GiftBonuses の内部名と UI 列名の写像が JS に漏れる

### 4.2. 疎マップ（採用）

* Good: 列キーが UI と 1:1 で、JS 側は写像なしで引くだけ。0 を含まないので転送が小さい
* Bad: キーが文字列契約になる（catalog の charKey と Rust の列キーの対応は
  カタログ側の doc コメントと恒等式テストで担保）

### 5.1. キャップを段階的に広げた増分で帰属（当初採用 → 2026-10-25 改訂で 5.2 に置換）

* Good: 「メリットポイントはスキル上限を 1 ランクにつき 2 広げ、上限 0 のスキルには効かない」という
  当時の計算規則と、表示値の求め方がそのまま対応する
* Bad: 計算規則が変わり（メリットポイントはスキル上限を広げず、上限で抑えた後に足す。
  [仕様書 0007](../specs/0007-status-calculation.md) の AC22）、段階的に広げる前提が成り立たなくなった

### 5.2. 基礎・ML・メリポ・ギフトを計算規則の項ごとに帰属（2026-10-25 改訂で採用）

* Good: 有効スキル値の定義の 4 つの和（0007 の用語「有効スキル値」）と行が 1 対 1 に近く、
  寄与の和が表示値に一致する
* Neutral: ML の行は、スキル上限をマスターレベル込みに広げたときの増分として残る
  （マスターレベルはスキル上限を広げるため）

    ジョブ及びレベルの組み合わせから求め、その上限にメリットポイントや装備の分を合計して実スキル値を求めるべき」
    と判断し、メリットポイントはスキル上限を広げず上限で抑えた後に足すと決めたため（0007 の制約、AC22・AC35）。
    この規則がゲームと合うかは一次情報で確かめていない（0007 の D5）。
  * どちらのジョブもスキルを持たないスキルも '-' にせず、メリットポイントと装備・ギフトの分を足す。
    同じ grill でのユーザーの判断（ゲームの仕様として、メインジョブが持たずサポートジョブが持つときと同じ形になる）。
  * 武器のスキル値にもギフトのスキルボーナスを足すと定義した（0007 の用語「武器のスキル値」）。
    ユーザーの指摘「武器スキルのギフトボーナスが今無いなら『足さない』と明記する理由が無く、
    明記すると将来追加されたときに誤りになる」による。
  * 武器のスキル値の列の装備行は、スロット専用 / 全スロット共通の振り分け（0007 の AC23・AC37）に従う。
    振り分けの規則の改訂と理由は [ADR 0018](0018-equip-module-owns-interpretation.md) の改訂の注記にある。
  * 常時表示ビューを 5 列にする決定と内訳の関係を追記した（Decision Outcome「常時表示ビューの 5 列との関係」）。
    内訳の設計は変えない。
  * 開いている間に計算の入力が変わったら求め直すことを追記した（0007 の AC28）。
  * 「装備 16 部位の行は JS 側で完結する」を、ADR 0018 以降の実装（スロット別の値も Rust の `EquipSet::bonuses` が求める）に合わせて直した。
