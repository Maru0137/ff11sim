# 0020. 未保存の編集を共通ガードで確認し、保存ボタンは編集時のみ有効にする

## Context and Problem Statement

装備セット編集フォームとキャラクター編集フォームは、編集の有無に関係なく保存ボタンが
常に押せる状態で、かつ編集を捨てる操作（装備セットのタブ切替、キャラ/ジョブセレクタの
変更、キャラクターの別レコードを開く、ログアウト、リロード）が無言で実行されていた。
「編集したときだけ保存ボタンを有効にし、編集内容が失われる操作には確認を出す」ために、
(a) 編集有無の判定方式、(b) 確認ダイアログの選択肢、(c) ガードを掛ける操作の範囲、
(d) 保存済み内容が前提の操作（複製・共有）の扱い、(e) ログイン同期による再読込の扱い
を決める必要がある。

2026-10-25 の改訂: 仕様書 0001・0002・0003・0006 の grill で、ガードを掛ける操作の範囲と
ログイン・ログアウトの確認の仕方を改めた。決めるべきことに次の 5 つを加える。
(f) ログイン・ログアウトで確かめる対象を 1 つにするか、すべてにするか、
(g) 画面の移動（サイドバー・ブラウザの「戻る」「進む」・URL の直接入力）を確認するか、
(h) 装備セットのタブの並べ替えを確認するか、
(i) カスタムステータスビューの編集画面を確認の対象にするか。
(e) の答えも改めた（5.2 → 5.3）。

## Decision Drivers

* 編集した値を元に戻したら「未編集」に戻ること（保存ボタンが押せるままだと嘘になる）
* 確認ダイアログを出す操作は、実際にデータが失われる操作だけであること
  （失われない操作で警告すると説明が事実と食い違い、「破棄」がむしろ害になる）。
  2026-10-25 の改訂で、キャラクター画面から別の画面へ移る操作だけをこの例外にした（7.2）
* 編集フォームは装備セット / キャラクターの 2 つがあり、今後増えても同じ規則で扱えること
  （2026-10-25 の改訂で、カスタムステータスビューの編集画面が 3 つ目になった）
* 装備セットの状態は React の外（`equipState` の可変オブジェクト）にあり、
  キャラクターフォームは React の `useState` にある — 判定方式を片方に寄せられないこと
* 「破棄して続行」の後に古い編集が残って、無関係な操作でダイアログが再発しないこと
* 1 回の操作で、確かめていない編集を失わないこと（2026-10-25 の改訂で追加。
  [仕様書 0001](../specs/0001-saving-and-sync.md) の制約「ログインとログアウトの未保存の確認ダイアログは…」）

## Considered Options

1. 編集有無（dirty）の判定方式
    - 1.1. 変更イベントで立てるフラグ
    - 1.2. 読み込み / 保存時のスナップショットと現在値の比較
2. 確認ダイアログの選択肢
    - 2.1. ブラウザ標準 `confirm`（続行 / キャンセルの 2 択）
    - 2.2. 2 択（破棄して続行 / キャンセル）の自前モーダル
    - 2.3. 3 択（保存して続行 / 破棄して続行 / キャンセル）の自前モーダル
3. ガードの実装位置
    - 3.1. 各画面がそれぞれ確認処理を持つ
    - 3.2. 共通レジストリ（DirtyEditor の登録）+ `guard()` に一元化
4. 複製・共有（保存済み内容が対象の操作）の扱い
    - 4.1. ガードを掛けて「保存して続行 / 破棄して続行」を選ばせる
    - 4.2. 未保存の間はボタンを無効化する
5. ログイン同期による再読込（`refreshEquipSetPanel`）とログイン・ログアウトの扱い
    - 5.1. 再読込処理の入口でガードする
    - 5.2. ログアウト操作をガードし、ログインは `beforeunload` に任せる（当初採用）
    - 5.3. ログアウトとログインの両方を、ボタンを押した時点で未保存の確認ダイアログでガードする
      （2026-10-25 改訂で採用）
6. ログイン・ログアウトで確かめる対象（2026-10-25 改訂で追加）
    - 6.1. 最初に見つかった 1 つの対象だけを確かめる（当初の実装）
    - 6.2. 未保存の変更を持つ対象をすべて挙げ、「保存して続行」は全部の保存を試し、
      失敗しても残りを試す
    - 6.3. すべて挙げるが、最初の保存の失敗で残りの保存をやめる
7. 画面の移動（サイドバー・ブラウザの「戻る」「進む」・URL の直接入力）（2026-10-25 改訂で追加）
    - 7.1. どの画面からの移動も確認しない（当初の決定）
    - 7.2. キャラクター画面からの移動だけを確認する
    - 7.3. すべての画面からの移動を確認する
8. 装備セットのタブの並べ替え（2026-10-25 改訂で追加）
    - 8.1. ガード対象にする（当初の決定）
    - 8.2. ガード対象から外す
9. カスタムステータスビューの編集画面（2026-10-25 改訂で追加）
    - 9.1. 対象にしない（当初の実装。この ADR は触れていなかった）
    - 9.2. 未保存の変更を持つ編集の対象として登録する

## Decision Outcome

選択: **1.2 + 2.3 + 3.2 + 4.2 + 5.3 + 6.2 + 7.2 + 8.2 + 9.2**
（2026-10-25 の改訂。当初の選択は 1.2 + 2.3 + 3.2 + 4.2 + 5.2 で、6〜9 は決めていなかった）。

- `web/src/dirty-guard.ts` に `DirtyEditor`（`label` / `isDirty` / `save` / `discard`）の
  レジストリと `guard(action, proceed, options)` を置く。編集内容が失われる操作は
  すべて `guard()` を通し、未保存なら `UnsavedChangesModal` を出して
  「保存して続行 / 破棄して続行 / キャンセル」を選ばせる。
- `save()` は `true | string` を返す（失敗理由を文字列で返す）。名前未入力・名前重複で
  保存できないときはダイアログを閉じずに理由を表示し、移動もしない。
  この規約に合わせて `saveEquipSet` / キャラクターの `save` は `alert` を返り値へ置き換え、
  ボタンから直接押されたときだけ呼び出し側が `alert` する。
- 「破棄して続行」は `proceed()` の前に `discard()` を呼ぶ。破棄したのに dirty が残ると、
  移動先で無関係な操作をしたときにダイアログが再発するため。
  装備セットの `discard()` は保存済みレコードの複製（`structuredClone`）を読み直す
  — スロットの値オブジェクトは装備選択モーダルが直接書き換えるので、控えは複製で持つ。
  キャラクターの `discard()` はフォームを閉じる。
- ガード対象は「実際に編集が失われる操作」と、例外としてキャラクター画面からの画面の移動に限る
  （2026-10-25 改訂。各画面の操作の一覧と操作の名前の正は仕様書の受け入れ基準）:
  - 装備セット: 選択中でないタブを押す / 新規 (+) / キャラ・ジョブセレクタの変更
    （[仕様書 0006 AC58](../specs/0006-equipset-editing.md)）。
  - キャラクター: 一覧の行の「編集」（開いているキャラクター自身を含む）/ 新規 / フォームを閉じる /
    キャラクター画面から別の画面へ移る操作
    （[仕様書 0002 AC47](../specs/0002-character-management.md)）。
  - カスタムステータスビュー: 編集画面の「戻る」「キャンセル」/ 編集画面のまま管理画面を閉じる
    （[仕様書 0003 AC16](../specs/0003-status-view-management.md)）。
  - 全体: ログイン、ログアウト、ページ離脱（`beforeunload`。再読み込みとタブを閉じるとき）
    （[仕様書 0001 AC8・AC22・AC36](../specs/0001-saving-and-sync.md)）。
- 装備セット画面など、キャラクター画面以外からのサイドバーでの画面の移動は対象外
  — 3 ビューは `display:none` で切り替えるだけでアンマウントされない（App.tsx）ため
  編集は失われない。
  サポートジョブの選択は装備セットレコードに保存されないため対象外。
  削除は既存の `confirm` に任せる（対象そのものを消す操作で、編集の消失は自明）。
- **キャラクター画面からの画面の移動**（2026-10-25 改訂）: キャラクター画面に未保存の変更が
  あるとき、サイドバー・ブラウザの「戻る」「進む」・URL の直接入力で別の画面へ移る操作も
  ガードする。移動では編集は失われないので、上の「実際に失われる操作だけ」の例外である。
  理由は仕様書 0002 の grill の決定による「装備セット画面には必ず保存済みのキャラクターで入るため。
  この理由は移動の経路によらず成り立つ」（[仕様書 0002](../specs/0002-character-management.md) の
  制約「キャラクター画面に未保存の変更があるとき…」）。
  対象は URL のハッシュだけが変わり、移動先がキャラクター画面以外のサイドバーの画面になるものに限る。
  「キャンセル」ではキャラクター画面のまま、ハッシュを `#/characters` に戻す（仕様書 0002 AC52）。
  ハッシュを戻すときにブラウザの履歴を積むか置き換えるかは未決（仕様書 0002 の D5）。
- **ログインとログアウト**（2026-10-25 改訂）: どちらもボタンを押した時点で `guard()` を通し、
  操作の名前を「ログイン」「ログアウト」とする。ダイアログは未保存の変更を持つ対象を、
  表示していない画面にあるものも含めてすべて挙げる。「保存して続行」は挙げた対象を 1 つずつ保存し、
  ある対象の保存に失敗しても残りをすべて試し、すべて保存できたときだけ操作を続ける。
  1 つでも保存できなければ、保存できなかった対象だけを挙げ直して理由を表示する。
  「破棄して続行」は挙げた対象すべてを `discard()` してから操作を続ける
  （[仕様書 0001 AC8・AC22〜AC24](../specs/0001-saving-and-sync.md)）。
  ダイアログを経て（または経ずに）認証画面へ移るときは、`beforeunload` のブラウザ標準の確認を出さない
  （仕様書 0001 AC8・AC36）。`beforeunload` に残るのは再読み込みとタブを閉じるときだけである。
  いまの `guard()` は 1 つの対象を確かめる形なので、すべての対象を扱う形を加える（形は実装で決める）。
- **装備セットのタブの並べ替え**（2026-10-25 改訂）: ガード対象から外す。並べ替えでは、
  読み込んでいる装備セットと選択中のタブを変えず、編集フォームの内容と未保存の変更をそのまま残す
  （[仕様書 0006 AC50・AC59](../specs/0006-equipset-editing.md)）。
  当初は並べ替えの後に移動した装備セットを読み込んでいた（`selectSet(moved.name)`）ため、
  編集が失われる操作としてガードしていた。
- **カスタムステータスビューの編集画面**（2026-10-25 改訂）: 編集画面の名前と表示するプロパティの列の
  変更を未保存の変更とし、`DirtyEditor` として登録する。対象の呼び名は
  「カスタムセット「<名前の入力欄の値>」」（[仕様書 0003 AC53](../specs/0003-status-view-management.md)）。
  ログイン・ログアウトで挙げる対象と、ページ離脱の確認にも含める（仕様書 0003 AC16）。
- 保存ボタンは未編集なら無効。複製・共有は保存済み内容に対する操作なので、
  未保存の間は無効にする。特に複製は編集中の `currentEquipSlots` からコピーを作って
  複製元の編集を捨てる挙動だったため、無効化でこの不整合ごと解消する。
  新規フォーム（まだ保存していない装備セット）でも、対象となる保存済み内容が無いので無効にする
  （2026-10-25 改訂で明記。[仕様書 0006 AC55](../specs/0006-equipset-editing.md) と、
  仕様書 0006 の制約「「複製」「共有」は新規フォームでも押せなくする」）。
- キャラクターフォームの「キャンセル」は「閉じる」に改名し中立色
  （`.btn-neutral`）にする。装備セット側と違いフォームを閉じる手段が他に無いので
  ボタン自体は残すが、役割は破棄ではなくクローズであり、未保存ならガードが確認する。
- セレクタ（controlled な `<select>`）のガードでは、キャンセル時に
  `notifyEquipState()` で再描画させる。state が変わらないと React は再描画せず、
  DOM だけユーザーが選んだ値のまま残るため。

### Consequences

* Good: 値を元に戻せば未保存表示も保存ボタンも自動的に戻る（フラグ方式の消し忘れが無い）。
* Good: 編集フォームを増やすときは `DirtyEditor` を 1 つ登録するだけで、
  ガード対象の操作側は変更不要（カスタムステータスビューの編集画面もこの形で加える）。
* Good: 「保存して続行」で移動をやめずに保存でき、保存できないときは理由が出たまま留まる。
* Good: ログインでも「保存して続行」を選べる（2026-10-25 改訂）。
* Good: ログイン・ログアウトの 1 回の操作で、確かめていない対象の編集が失われない（2026-10-25 改訂）。
* Bad: dirty 判定が毎レンダーの JSON 比較になる（装備 16 スロット + キャラクターフォーム全体）。
  実測で問題になる規模ではないが、比較対象を増やすとレンダーごとのコストが増える。
* Bad: 装備セット側は「保存対象のフィールド」を `equip-set-snapshot.ts` で明示的に
  列挙しているため、保存レコードに項目を足したらスナップショットにも足す必要がある。
* Bad: キャラクター画面からの画面の移動では、編集が失われないのに確認が出る
  （ドライバ「実際にデータが失われる操作だけ」の例外。2026-10-25 改訂）。
* Bad: ログイン・ログアウトのダイアログは、複数の対象・保存できなかった対象の挙げ直し・
  対象ごとの保存の競合の警告（仕様書 0001 AC47）を扱う必要があり、1 対象の確認より複雑になる。
* Bad: 再読み込みとタブを閉じるときの確認はブラウザ標準の `beforeunload` ダイアログのままで、
  文言を制御できない。
* Neutral: キャラクター画面以外ではビュー切替をガードしないので、「装備検索で調べてから戻る」動線は
  無警告のまま維持される（編集も維持される）。

## Pros and Cons of the Options

### 1.1. 変更イベントでフラグを立てる

* Good: 判定が O(1) で実装も最小
* Bad: 値を元に戻しても未保存のままになり、保存ボタンが押せる状態が残る
* Bad: 変更経路（スロット選択モーダル・オーグメント・カスタム説明・プロパティセット選択）
  ごとにフラグ立てを足す必要があり、追加漏れが静かに起きる

### 1.2. スナップショット比較（採用）

* Good: 変更経路を知らなくてよい。判定は「今の値」だけを見る
* Good: 元に戻せば未保存でなくなる
* Bad: 比較のたびに JSON 化のコストがかかる
* Bad: 何を比較対象にするかを明示的に決める必要がある（表示用フィールドを含めると
  同じ装備の再選択が変更として出る）

### 2.1. ブラウザ標準 `confirm`

* Good: 実装が要らない
* Bad: 「保存して続行」を出せず、保存したいユーザーは一度キャンセルして保存し直す必要がある
* Bad: 文言・ボタンラベルを制御できない

### 2.2. 2 択の自前モーダル

* Good: 実装が単純で、選択肢が少なく迷わない
* Bad: 「保存し忘れ」が主因なのに、その場で保存できない

### 2.3. 3 択の自前モーダル（採用）

* Good: 保存し忘れをその場で解決でき、往復が要らない
* Bad: 保存できない状態（名前未入力・重複）を扱う必要があり、
  ダイアログ内にエラー表示と「留まる」分岐が要る

### 3.1. 各画面が個別に確認処理を持つ

* Good: 画面ごとに文言や選択肢を自由にできる
* Bad: 確認を通す操作が増えるたびにコピーが増え、抜けが出る
* Bad: `beforeunload` やログアウトのような「どの画面が未保存かを知りたい」処理から
  横断的に問い合わせられない

### 3.2. 共通レジストリ + `guard()`（採用）

* Good: 「編集が失われる操作は `guard()` を通す」という 1 つの規則で済む
* Good: `isAnyDirty()` で画面をまたいだ判定ができ、`beforeunload` が 1 箇所で書ける
* Bad: エディタの `save` / `discard` を後から差し替える必要があり、
  React 側では ref 経由の登録という一手間が要る

### 4.1. 複製・共有もガードする

* Good: 操作を止めない（未保存でも先に進める）
* Bad: 複製は「編集中の内容でコピーを作り、複製元の編集は捨てる」挙動なので、
  ダイアログで説明しきれない結果になる
* Bad: 共有は保存済み内容を共有するため、画面と共有結果が食い違ったままになりうる

### 4.2. 未保存の間は無効化する（採用）

* Good: 押せた時点で「画面の内容 = 保存済みの内容」が保証され、上記の食い違いが消える
* Good: 実装が単純（ガードの分岐が増えない）
* Bad: 複製したいだけでも先に保存が必要になる

### 5.1. 再読込処理の入口でガードする

* Good: 再読込でデータが入れ替わる箇所を直接押さえられる
* Bad: 再読込が走るのは実質ログイン完了後（`onAuthChange` / `ff11sim:synced`）で、
  その時点ではログインは終わっておりユーザーに取れる手が無い。
  しかもログインは OAuth リダイレクトでページを離れるため、
  戻ってきた時点で編集内容はそもそも存在しない
* Bad: `refreshEquipSetPanel` は起動時初期化からも呼ばれ、ガードの対象を選り分ける条件が要る

### 5.2. ログアウト操作をガードし、ログインは `beforeunload` に任せる（当初採用 → 2026-10-25 改訂で 5.3 に置換）

* Good: ダイアログの 3 択がすべて意味を持つ（保存してログアウト / 破棄してログアウト /
  ログアウトしない）
* Good: 認証リスナはユーザー ID が変わったときだけ発火する（`supabase-client.ts`）ため、
  トークン更新やタブ復帰で誤発火しない
* Bad: ログイン時の確認はブラウザ標準文言になる
* Bad: ログインでは「保存して続行」を選べず、保存したい利用者は一度キャンセルして保存し直す必要がある
* Neutral: リアルタイム購読やポーリングは無く、他端末の変更が勝手に降ってくることはないため、
  外部要因の再読込はこの 2 経路以外に存在しない

### 5.3. ログアウトとログインの両方をボタンの時点でガードする（2026-10-25 改訂で採用）

仕様書 0001 の grill で決定。理由は「ログインはアプリ内のボタンから始まるので認証画面へ移る前に
ダイアログを出せ、ログアウトと同じ仕組みで『保存して続行』を選べるようにするため」
（[仕様書 0001](../specs/0001-saving-and-sync.md) の制約「未保存の確認は、ログインとログアウトでは…」）。

* Good: ログインとログアウトが同じ仕組み・同じ 3 択になる
* Good: 5.2 の「認証リスナはユーザー ID が変わったときだけ発火する」利点はそのまま保たれる
  （ガードはボタンの時点で掛け、再読込の入口には掛けない）
* Bad: ダイアログを経て認証画面へ移るときに `beforeunload` の確認が重ねて出ないようにする必要がある
  （仕様書 0001 AC8）

### 6.1. 最初に見つかった 1 つの対象だけを確かめる（当初の実装）

* Good: `guard()` の 1 対象の形をそのまま使える
* Bad: ログアウト 1 回で、確かめていない他の対象の編集を失いうる

### 6.2. すべて挙げ、全部の保存を試し、失敗しても残りを試す（2026-10-25 改訂で採用）

仕様書 0001 の grill で決定。理由は「1 つの対象だけを確かめると、操作 1 回で他の対象の編集を
確かめずに失いうるため。1 回の操作で保存できるものを全部保存するため」
（[仕様書 0001](../specs/0001-saving-and-sync.md) の制約「ログインとログアウトの未保存の確認ダイアログは…」）。

* Good: どの対象の編集も確かめずに失われない
* Good: 1 つの失敗で、保存できた他の対象まで保存されずに残ることが無い
* Bad: 保存できなかった対象の挙げ直しと、対象ごとの競合の警告（仕様書 0001 AC47）を扱う分岐が要る

### 6.3. すべて挙げるが、最初の失敗で残りの保存をやめる

* Good: 失敗したら即座に止まり、処理が単純
* Bad: 保存できたはずの対象が保存されずに残る

### 7.1. どの画面からの移動も確認しない（当初の決定）

* Good: 3 ビューは `display:none` で切り替えるので編集は失われず、ドライバ「失われる操作だけ」に沿う
* Good: 「装備検索で調べてから戻る」動線を妨げない
* Bad: キャラクター画面に未保存の変更を残したまま別の画面へ移れる。仕様書 0002 の grill では
  「装備セット画面には必ず保存済みのキャラクターで入る」ことを求めたため、この案を退けた

### 7.2. キャラクター画面からの移動だけを確認する（2026-10-25 改訂で採用）

仕様書 0002 の grill（0002-Q5、R1 の問い Q2）で決定。理由は 7.1 の Bad のとおり
（[仕様書 0002](../specs/0002-character-management.md) の制約「キャラクター画面に未保存の変更があるとき…」）。

* Good: 装備セット画面には保存済みのキャラクターで入ることが、移動の経路によらず保たれる
* Good: 装備セット画面からの移動は確認しないので、7.3 の Bad が起きない
* Bad: 編集が失われない操作で確認が出る（ドライバの例外）
* Bad: ブラウザの「戻る」「進む」でハッシュが変わった後に確認するので、「キャンセル」で
  ハッシュを戻す処理が要る（履歴を積むか置き換えるかは仕様書 0002 の D5）

### 7.3. すべての画面からの移動を確認する

* Good: 画面ごとに規則を分けなくて済む
* Bad: 装備セット画面で、装備検索を見に行って戻る使い方を妨げる
  （仕様書 0006 の grill の決定 0006-Q7 で、装備セット画面からの移動は確認しないと決めた理由）

### 8.1. 装備セットのタブの並べ替えをガードする（当初の決定）

* Good: 並べ替えの後に移動した装備セットを読み込む当初の実装では、失われる編集を確かめられる
* Bad: 並べ替えるだけで確認が出る

### 8.2. ガード対象から外す（2026-10-25 改訂で採用）

仕様書 0006 の grill で決定。理由は「並べ替えは装備セットの中身を変えず、読み込み直さなければ
編集内容は失われないので、『実際に編集内容が失われる操作だけ』に沿う」
（[仕様書 0006](../specs/0006-equipset-editing.md) の制約「並べ替えでは、読み込んでいる装備セットと…」）。

* Good: ドライバ「失われる操作だけ」とキャラクター一覧の並び替え（[ADR 0022](0022-character-list-order.md) の 4.2）に揃う
* Bad: 並べ替えの後に、移動した装備セットを読み込まない形へ実装を変える必要がある

### 9.1. カスタムステータスビューの編集画面を対象にしない（当初の実装）

* Good: モーダル内の短い編集で、確認の手間が無い（R1 の点検で、残す理由として推測で挙がったもの）
* Bad: 「戻る」や管理画面を閉じたときに名前と列の変更が黙って捨てられ、ログアウトの確認の対象にも入らない
* Bad: 「編集内容が失われる操作は、編集の対象の種類によらず共通の仕組みを通して確認する」
  （仕様書 0001 の制約）と食い違う

### 9.2. 未保存の変更を持つ編集の対象として登録する（2026-10-25 改訂で採用）

仕様書 0003 の grill（R1 の問い Q8。推奨とは別の案をユーザーが選択）で、0001 と揃えると決定。

* Good: 3 つの編集フォームが同じ規則・同じダイアログになる
* Good: ログイン・ログアウト・ページ離脱の確認に含まれる
* Bad: 編集画面の「戻る」「キャンセル」と、管理画面の閉じ方 3 通り（「×」・Esc・外側を押す）を
  すべて `guard()` に通す必要がある
