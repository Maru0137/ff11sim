# 0008. 装備セット共有は公開 SELECT の `shared_equipsets` テーブルとキャラクタースナップショットで実現する

## Context and Problem Statement

作った装備セットを他人に見せたいという要求がある。しかし装備セットだけを渡しても、
閲覧側では同じステータス値を再現できない。FFXI のステータスは種族・ジョブレベル・
マスターレベル・スキル・メリットポイント・ジョブポイントに依存するためである。
何を、どこに、どの公開範囲で置くかを決める必要がある。

## Decision Drivers

* 共有相手にログインを要求しないこと（URL を開くだけで見られること）
* 共有された状態で、作成者と同じ数値が再現されること
* URL が現実的な長さに収まること
* 実装が [ADR 0005](0005-localstorage-default-supabase-optin.md) の永続化と衝突しないこと

## Considered Options

1. URL に全データを埋め込む（クエリ文字列またはフラグメント）
2. 共有用テーブルに保存し、`?share=<uuid>` で参照する
    - 2.1. 装備セットのみ保存し、閲覧者自身のキャラクターで計算させる
    - 2.2. 作成時点のキャラクタースナップショットも一緒に保存する
3. 既存の `equipsets` 行に公開フラグを立てて共有する

## Decision Outcome

選択: **2 + 2.2. 共有テーブル + キャラクタースナップショット**（採用）。

URL 埋め込み（選択肢 1）は、16 スロット分の装備とオーグメント、さらにキャラクター情報を
含めると URL が実用にならない長さになる。既存 `equipsets` への公開フラグ（選択肢 3）は、
共有後に元セットを編集すると共有内容が勝手に変わり、かつ RLS ポリシーが
「自分の行のみ」と「公開行は全員」の 2 条件で複雑化する。共有は独立した不変のレコードとする。

- `shared_equipsets` テーブルを `equipsets` とは別に用意する。
- RLS は次の 3 ポリシー:
  * SELECT: `using (true)` — 未ログインを含む全員が読める。URL を知っていれば閲覧可。
  * INSERT: `with check (auth.uid() = user_id)` — 認証ユーザーのみ作成可（スパム抑止）。
  * DELETE: `using (auth.uid() = user_id)` — 作成者のみ削除可。
- `name` / `character_name` / `job` は列に展開し、`slots` などは `data` jsonb に格納する。
  キャラクタースナップショットは `data.character` に入れる。
- 共有 URL は `<origin><pathname>?share=<uuid>`。
- **共有内容は作成時点のスナップショットであり、元の装備セットを編集しても追従しない。**
  これは意図した挙動とする。
- 閲覧者はスナップショットを読み取り専用の復元計算にのみ使い、自分のデータを上書きしない。
  インポート時は閲覧者自身のキャラクターとジョブを選び直させる。

### Consequences

* Good: 共有 URL が短く、SNS 等で扱える。
* Good: 閲覧にログインが要らない。
* Good: 作成者と同じ数値が再現される。「見えている数値が作成者の意図した数値」になる。
* Good: 共有レコードが独立しているため、元セットの編集・削除が共有を壊さない。
* Bad: **実質的に公開データである。** キャラクター名・種族・レベル・スキル・
  メリット/ジョブポイントが、URL を知る全員に読める。UUID による難推測性のみが
  アクセス制御であり、認可はかかっていない。
* Bad: 誤って共有した場合、取り消しは DELETE のみ。既に閲覧・保存された分は取り戻せない。
* Bad: 共有レコードは増え続ける。期限切れ削除や上限の仕組みがなく、GC もない。
* Bad: 共有一覧・管理画面がないため、作成者が自分の共有を後から把握・削除する手段が
  実質的にない（DELETE ポリシーだけが用意されている状態）。
* Neutral: スナップショットのため元セットに追従しない。更新を反映したい場合は
  共有し直すことになる。

### Confirmation

* `supabase/schema.sql` および `supabase/migrations/002_shared_equipsets.sql` が
  `shared_equipsets` に対して以下のポリシーを定義している:
  `for select using (true)` / `for insert with check (auth.uid() = user_id)` /
  `for delete using (auth.uid() = user_id)`。
* `web/js/share.js` の `createShare()` は `getCurrentUser()` が null なら
  例外を投げ、未ログインでの作成を防ぐ（RLS と二重の防御）。
* `loadSharedEquipSet()` は `data.character` を `characterSnapshot` として分離して返し、
  呼び出し側が装備セット本体と区別して扱えるようにしている。

検証されていないもの:

* 共有機能の自動テストは存在しない。CI は `cargo test` のみを実行する
  （[ADR 0001](0001-rust-wasm-static-site.md)）。
* RLS ポリシーが実 DB に適用されているかは検証されていない
  （[ADR 0007](0007-supabase-anon-key-ci-injection.md) と同じ手動適用の問題）。
* 共有時に「この内容は URL を知る全員に公開される」とユーザーへ明示しているかは
  UI 実装側の責務であり、本 ADR では保証していない。

フォローアップ候補: 共有作成時に公開範囲を明示する警告文を出す。作成した共有の
一覧と削除 UI を用意する。

## Pros and Cons of the Options

### 1. URL に全データを埋め込む

* Good: サーバー側に何も保存しないため、データの寿命や GC を考えなくてよい。
  [ADR 0001](0001-rust-wasm-static-site.md) のサーバーレス志向と最も整合する。
* Good: 共有レコードが存在しないので、蓄積・漏洩・削除の管理が不要。
* Good: 未ログインでも共有 URL を作成できる。
* Bad: 16 スロットの装備・オーグメント・キャラクター情報を含めると
  URL が実用にならない長さになる。
* Bad: SNS やチャットの文字数制限で切り詰められて壊れる。
* Bad: 埋め込みフォーマットを変更すると、過去に配った URL が読めなくなる。

### 2. 共有用テーブルに保存し、`?share=<uuid>` で参照する（採用）

* Good: URL が短く、どこにでも貼れる。
* Good: 保存形式を後から変更しても、読み出し側で吸収できる。
* Bad: 共有レコードが蓄積し続ける。期限や上限の設計が別途必要になる。
* Bad: 閲覧側まで Supabase に依存する。DB が落ちると共有 URL が開けない。

#### 2.1. 装備セットのみ保存し、閲覧者自身のキャラクターで計算させる

* Good: 保存するデータが小さく、他人のキャラクター情報を公開せずに済む。
  プライバシーの観点では明確に優れる。
* Bad: 閲覧者に表示される数値が作成者のものと一致しない。
  「この装備でこの数値が出る」という共有の目的を果たせない。
* Bad: 閲覧者がキャラクターを持っていない（未ログイン・初回訪問）と何も表示できない。

#### 2.2. 作成時点のキャラクタースナップショットも一緒に保存する（採用）

* Good: 作成者と同じ数値が再現される。共有の目的を果たす。
* Good: 閲覧者が自分のキャラクターを持っていなくても表示できる。
* Bad: キャラクター名・種族・レベル・スキル・メリット/ジョブポイントが
  URL を知る全員に読める。
* Bad: スナップショットのため元データに追従しない。更新を反映するには共有し直す必要がある。

### 3. 既存の `equipsets` 行に公開フラグを立てて共有する

* Good: テーブルが増えず、データの重複がない。
* Good: 元セットを更新すれば共有内容も自動で最新になる。
* Bad: 共有後に元セットを編集すると、共有した覚えのない内容が公開される。
* Bad: RLS が「自分の行は全操作可」と「公開行は全員 SELECT 可」の 2 条件になり複雑化する。
  [ADR 0007](0007-supabase-anon-key-ci-injection.md) の通り安全性を RLS に全面依存しているため、
  ポリシーの複雑化がそのままリスクになる。
* Bad: 元セットを削除すると共有 URL が死ぬ。
