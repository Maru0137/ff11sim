# 0005. 永続化は localStorage を既定とし、Supabase をオプトインにする（Repository で切り替える）

## Context and Problem Statement

キャラクターと装備セットはユーザーが時間をかけて作るデータであり、端末をまたいで
使いたいという要求がある。一方でログインを必須にすると、試しに触ってみたいだけの
ユーザーを門前払いすることになる。サーバーを持たない構成
（[ADR 0001](0001-rust-wasm-static-site.md)）の下で、どこに保存し、
認証の有無をアプリケーションコードにどう見せるかを決める必要がある。

## Decision Drivers

* ログインなしで全機能が使えること（導入障壁をゼロに保つ）。例外は共有の作成だけで、
  これはログインを前提とする（[ADR 0008](0008-equipset-sharing.md)、
  [仕様書 0001](../specs/0001-saving-and-sync.md) の S1・AC5、
  [仕様書 0009](../specs/0009-equipset-sharing.md) の AC5。2026-10-25 改訂で明記）
* ログインすれば端末間でデータを共有できること
* UI コードが認証状態の分岐で汚れないこと
* 個人開発として維持する実装量に収まること
* 2 つの画面（タブや端末）で同じデータを保存しても、別の画面で保存された変更や、
  読み込みに失敗して見えていないデータを黙って消さないこと（2026-10-25 改訂で追加。
  [仕様書 0001](../specs/0001-saving-and-sync.md) の P5・P6）

## Considered Options

1. localStorage のみを使う（クラウド保存をあきらめる）
2. Supabase のみを使う（ログインを必須にする）
3. 両方に対応する
    - 3.1. 呼び出し側で認証状態を見て分岐する
    - 3.2. Repository 抽象を挟み、facade の背後に隠す

3.1 と 3.2 は「分岐をどこに置くか」で分かれる。

2026-10-25 の改訂で、Repository の保存の粒度と識別キーについて次の選択肢を足した。

4. 保存の粒度
    - 4.1. 一覧全体を渡し、保存先の既存一覧との差分を取って書く（当初採用 → 2026-10-25 改訂で 4.2 に置換）
    - 4.2. 保存の直前に保存先を読み直し、変えた競合の単位 1 つだけを差し替えて書く
5. 識別キー
    - 5.1. 名前で識別する（キャラクターは `(user_id, name)`、装備セットは
      `(user_id, name, character_name, job)`）（当初採用 → 2026-10-25 改訂で 5.2 に置換）
    - 5.2. 作った時点に端末側で振る不変の ID（キャラクターの ID・装備セットの ID）で識別する

## Decision Outcome

選択: **3 + 3.2. Repository 抽象を挟み、facade の背後に隠す**（採用）。
保存の粒度と識別キーは **4.2 + 5.2**（当初は 4.1 + 5.1。2026-10-25 の改訂で変更）。

未ログインで使えることは譲れず（選択肢 2 を却下）、端末間共有の要求も実在する
（選択肢 1 を却下）。両対応が前提になると、分岐を呼び出し側に散らす 3.1 は
永続化を触るすべての箇所に認証の知識を要求してしまうため、境界を 1 箇所に閉じ込める。

- 呼び出し側は `web/js/storage.js` の `loadCharacters` / `saveCharacters` /
  `loadEquipSets` / `saveEquipSets` のみを使う。認証状態を見てはならない。
  （関数名と引数は当初の決定のもの。4.2 の粒度に合わせて入口の形は変わる。新しい形は未決で、
  実装のときに決める。ファイルはその後 `web/src/storage.ts` に移った。）
- `storage.js` は `getCharacterRepo()` / `getEquipSetRepo()` に委譲するだけの facade とし、
  自身は localStorage を直接触らない。
- 各 repo ファクトリが `getCurrentUser()` の有無で `Local*Repo` / `Supabase*Repo` を返す。
- 保存は、保存先へ書く直前に保存先から保存しようとした競合の単位を読み直し、その 1 つだけを
  差し替えて書く。保存しようとしたもの以外の競合の単位は、別の画面で保存されたものも、
  この画面に表示していないものも変えない。localStorage と Supabase の両方に当てはまる
  （[仕様書 0001](../specs/0001-saving-and-sync.md) の AC39。例外 2 つも同 AC のとおり）。
  競合の単位は、キャラクター 1 人・装備セット 1 つ・カスタムステータスビュー 1 つ・
  ユーザー定義プロパティ 1 つである（仕様書 0001 の用語「競合の単位」。
  カスタムステータスビューとユーザー定義プロパティの保存の形は
  [ADR 0015](0015-property-sets.md) が扱う）。
  - 読み直した内容が、この画面に読み込んだ（または最後に保存した）時点の内容と異なれば、
    書く前に競合の警告を出す。判定と書き込みは不可分に行う（仕様書 0001 の AC40・AC58）。
    不可分にする手段は未決（仕様書 0001 の D5・D9）。
  - 削除は競合の単位 1 つを消し、並び替えは読み直した一覧に並び順だけを当てて書き、
    複製は新しい 1 件を加えるだけである（仕様書 0001 の AC43〜AC46）。
  - 複数のデータの種類、または複数の競合の単位に書く操作は 1 回の書き込みにまとめる
    （仕様書 0001 の AC53）。手段は未決（仕様書 0001 の D8）。
  - 2026-10-25 の改訂で、当初の「インターフェースは `list()` と `save(配列)` の 2 つだけに絞り、
    Supabase 側は `save` のたびに既存一覧との差分を取って upsert と delete を発行する」（4.1）を
    置き換えた。理由: 一覧全体を書くと、別の画面で保存された他の件や、読み込みに失敗して
    見えていない件を消しうるため（仕様書 0001 の grill で決定。同仕様書の制約の節）。
- 識別キーは、キャラクターはキャラクターの ID、装備セットは装備セットの ID とし、
  Supabase 側の一意制約と一致させる。装備セットは所属するキャラクターをキャラクターの ID で指す。
  名前は識別キーにせず、重複を禁じる制約としてだけ残す（キャラクターは前後の空白を除いた名前が
  保存先の中で重複しない、装備セットは同じキャラクターとジョブの中で名前が重複しない。
  [仕様書 0002](../specs/0002-character-management.md) の AC3、
  [仕様書 0006](../specs/0006-equipset-editing.md) の AC1）。重複の禁止をほぼ同時の保存でも
  保証する手段は未決（仕様書 0002 の D9）。
  - 2026-10-25 の改訂で、当初の識別キー（character が `(user_id, name)`、equipset が
    `(user_id, name, character_name, job)`）（5.1）を置き換えた。理由: 名前で識別すると、
    名前を変えたときに装備セットとキャラクターの結び付きが切れ、名前を変えた後に同じものだと
    判定する手がかりも無く、別の画面での名前の変更を保存の競合や保存先から消えていた場合と
    区別できないため（仕様書 0002・0006 の grill で決定。各仕様書の制約の節）。
- ID は端末側で振る。キャラクターの ID は新規のキャラクターの編集フォームを開いた時点で
  振る UUID である（仕様書 0002 の AC38）。装備セットの ID は新規フォームを開いた時点で振る
  （仕様書 0006 の AC75）。どちらも保存に失敗して保存し直しても同じ ID を使い、
  端末内データとアカウントデータを通じて一意である。複製・インポート・
  「新しい … として保存」では新しい ID を振る（仕様書 0002 の AC44、仕様書 0006 の AC24・AC75）。
- ID の無い既存データ（localStorage・Supabase の両方）を ID へ移す方法は未決で、
  別の ADR に記録する（仕様書 0002 の D1、仕様書 0006 の D2）。
- 読み込みに失敗したときは、0 件と区別して画面に表示し、そのデータの種類の書き込みを止める
  （仕様書 0001 の AC4。2026-10-25 改訂で追記）。区別して伝える内部の手段は未決
  （仕様書 0001 の D3）。
- API はすべて async。呼び出し側は `await` が必須。
- 例外として **UI プリファレンス層** を認める（[ADR 0015](0015-property-sets.md) で追記）:
  消えても実害のない端末ローカルの UI 状態（サイドバー開閉 `ff11sim_nav_collapsed`）は
  facade を通さず localStorage に直接保存し、Supabase には同期しない。頻繁な書き込みが
  全件 upsert を誘発しないようにするためで、ユーザーデータ本体には適用しない。
  （プロパティセット選択記憶は当初この層だったが、[ADR 0015](0015-property-sets.md) の
  2026-08-13 改訂で装備セットレコードへ移動した。）
- 未ログインで使えないのは共有の作成だけである（[ADR 0008](0008-equipset-sharing.md)）。
  共有の閲覧とインポートはログインしていなくても行える
  （[仕様書 0009](../specs/0009-equipset-sharing.md) の AC3・AC32。2026-10-25 改訂で明記）。

### Consequences

* Good: 未ログインでも、共有の作成を除き、キャラクター作成・装備セット・計算のすべてが動く。
* Good: UI 側は認証状態を意識せず、同じ関数を呼ぶだけで済む。
* Good: 保存先の追加・変更が repo の追加で済む。
* Good: 1 件の保存が他の件を書き換えないので、別の画面で保存された変更や、
  読み込みに失敗して見えていない件を消さない（2026-10-25 改訂）。
* Good: キャラクターの名前を変えても、装備セットとの結び付きが切れない（2026-10-25 改訂）。
* Bad: 永続化の実装を 2 系統維持し続ける必要がある。片方だけ修正する事故が起こりうる。
* Bad: 保存のたびに保存先を読み直し、競合を判定してから書くため、当初の差分保存より
  1 回の保存の手順が増える。判定と書き込みを不可分にする仕組み（Supabase 側の条件付き更新や
  タブ間の排他など）も 2 系統それぞれに要る（2026-10-25 改訂）。
* Bad: ID の無い既存データを移す処理が必要になる（2026-10-25 改訂）。
* Bad（当初の決定のもの。4.1 の置き換えで解消する）: `save` が「全件を渡して差分を取る」
  粒度のため、1 件の編集でも全件の upsert が飛ぶ。equipset の削除は複合キーのため
  1 件ずつ DELETE を発行しており、データ量に比例してリクエストが増える。
* Bad（当初の決定のもの。仕様書 0001 の AC4 で改める）: `list()` は Supabase 側でエラーが
  起きたとき `console.error` して空配列を返す。呼び出し側からは「データが 0 件」と区別がつかず、
  保存操作と組み合わさると意図しない削除につながる可能性がある。
* Bad: localStorage 側は容量上限（一般に数 MB）があり、装備セットが増えると
  保存に失敗しうるが、失敗を検知して通知する処理はない（仕様書 0001 の AC42 は
  保存の失敗を通知すると定める）。
* Neutral: 並び順は Supabase では `position` 列で保持し、localStorage では配列順で保持する。
  1 件だけを書く保存での新しい件の位置の振り方は未決（仕様書 0002 の D11、
  [ADR 0022](0022-character-list-order.md)）。
* Neutral: 同期の方向と初回アップロードは本 ADR の範囲外とし、
  [ADR 0006](0006-login-sync-conflict-resolution.md) で決める。

### Confirmation

* `web/js/storage.js` は repo に委譲するのみで、localStorage を直接参照していない
  （2026-08-02 時点の実装で確認済み。ファイルはその後 `web/src/storage.ts` に移った）。
* `web/js/repositories/character-repo.js` / `equipset-repo.js` の
  `getCharacterRepo()` / `getEquipSetRepo()` が `getCurrentUser()` の結果で
  実装を切り替える（同上。今は `web/src/repositories/*.ts`）。

2026-10-25 の改訂の内容は未実装（仕様書 0001・0002・0006 の受け入れ基準と実装の差。issue 化予定）:

* 1 つの競合の単位だけを差し替える保存と、保存の競合の判定（仕様書 0001 の AC39・AC40・AC58）。
  今の `web/src/repositories/character-repo.ts`・`equipset-repo.ts` は一覧全体を
  `onConflict: 'user_id,name'`・`'user_id,name,character_name,job'` で upsert している。
* キャラクターの ID・装備セットの ID による識別と、ID を振る時点（仕様書 0002 の AC38、
  仕様書 0006 の AC75）。
* 読み込みの失敗を 0 件と区別すること（仕様書 0001 の AC4）。

検証されていないもの:

* Repository の自動テストは存在しない。CI で走るのは `cargo test` のみであり
  （[ADR 0001](0001-rust-wasm-static-site.md)）、Web 側の永続化はテスト対象外。
* facade を迂回して localStorage を直接読む箇所が新たに追加されても検出できない。
  現状 `web/js/sync.js` は同期処理の性質上、また UI プリファレンス層
  （`ff11sim_nav_collapsed`）は上記の例外規定により、
  意図的に localStorage を直接読み書きしている。

## Pros and Cons of the Options

### 1. localStorage のみを使う

* Good: 実装が最も単純。認証もネットワークも要らない。
* Good: [ADR 0001](0001-rust-wasm-static-site.md) のサーバーレス志向と完全に一致する。
* Bad: 端末間でデータを共有できない。ブラウザのデータを消すと失われる。
* Bad: 装備セット共有 ([ADR 0008](0008-equipset-sharing.md)) のような機能を後から載せられない。

### 2. Supabase のみを使う（ログインを必須にする）

* Good: 保存先が 1 つで、実装とテストの対象が半分になる。
* Good: 端末間共有が自然に得られる。
* Bad: 試しに触ってみたいだけのユーザーにログインを強制する。導入障壁として大きい。
* Bad: Supabase が落ちるとアプリが一切使えなくなる。
* Bad: 未ログインでも成立すべき装備検索ページの位置づけが破綻する。

### 3. 両方に対応する（採用）

* Good: 未ログインで全機能が使え、ログインすれば端末間で共有できる。
* Good: Supabase に障害があってもゲストとしては使い続けられる。
* Bad: 永続化の実装を 2 系統維持し続ける必要がある。
* Bad: 2 つの保存先の間でデータをどう移すかという別の問題が生じる
  （[ADR 0006](0006-login-sync-conflict-resolution.md)）。

#### 3.1. 呼び出し側で認証状態を見て分岐する

* Good: 抽象化の層が増えず、処理の流れがその場で読める。
* Bad: 永続化を触るすべての箇所に認証の知識が要る。追加のたびに分岐を書き忘れる余地が残る。
* Bad: 保存先を増やすときに全呼び出し箇所を直すことになる。

#### 3.2. Repository 抽象を挟み、facade の背後に隠す（採用）

* Good: UI 側は認証状態を意識せず、同じ関数を呼ぶだけで済む。
* Good: 分岐が repo ファクトリの 1 箇所に閉じ、保存先の追加が repo の追加で済む。
* Bad: API がすべて async になり、既存の同期呼び出しを `await` に書き換える必要があった。

### 4. 保存の粒度

#### 4.1. 一覧全体を渡して差分を取る（当初採用 → 2026-10-25 改訂で 4.2 に置換）

* Good: インターフェースが `list` / `save` の 2 つで済み、実装が小さい。
* Bad: 1 件だけ更新したい場合も全件を渡すことになる。
* Bad: 画面が持つ一覧が保存先と食い違っていると、別の画面で保存された他の件や、
  読み込みに失敗して見えていない件を上書き・削除しうる。改訂の理由になった。

#### 4.2. 読み直して競合の単位 1 つだけを差し替える（採用）

* Good: 保存しようとしたもの以外を変えない。
* Good: 読み直した内容で保存の競合を判定でき、後勝ちで黙って上書きしない。
* Bad: 保存の手順が増え、判定と書き込みを不可分にする仕組みが 2 系統それぞれに要る。

### 5. 識別キー

#### 5.1. 名前で識別する（当初採用 → 2026-10-25 改訂で 5.2 に置換）

* Good: 利用者に見える名前がそのままキーで、ID を振る処理も移行も要らない。
* Bad: キャラクターの名前を変えると、名前で指している装備セットとの結び付きが切れる。
* Bad: 名前を変えた後に同じものだと判定する手がかりが無く、別の画面での名前の変更を
  保存の競合と区別できない。改訂の理由になった。

#### 5.2. 不変の ID で識別する（採用）

* Good: 名前を変えても同じもののままで、結び付きも競合の判定も ID で決まる。
* Good: 初回アップロードで ID をそのまま送れる（[ADR 0006](0006-login-sync-conflict-resolution.md)）。
* Bad: 名前の重複の禁止を、識別キーとは別の制約として保証する必要がある。
* Bad: ID の無い既存データの移行が要る。
