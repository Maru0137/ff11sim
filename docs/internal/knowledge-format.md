# ナレッジの書き方

[docs/internal/knowledge/](knowledge/) には、FINAL FANTASY XI のゲームがどう動くか（計算式・ゲーム仕様・データの性質）を記録する。
後から式や値の妥当性を確かめられるよう、主張ごとに出典をたどれる形で書く。この文書はその形を定める。

## OKF に従う

`docs/internal/knowledge/` は、OKF（Open Knowledge Format）v0.2 のバンドルとして書く。OKF は、YAML の frontmatter
付きの Markdown ファイルを並べたディレクトリで知識を表す形式で、仕様は
[okf/SPEC.md](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/62432a0/okf/SPEC.md) にある。
バンドルはその配布単位のディレクトリ、コンセプトはバンドルの中の Markdown ファイル 1 本を指す。

OKF の規則のうち、このバンドルで守るのは次の点である。

- `index.md` と `log.md` 以外の `.md` はすべてコンセプトで、frontmatter を持つ（SPEC §3.1、§11）。
  そのため、この文書のようなバンドルについての説明はバンドルの外に置く。
- バンドルの root に `index.md` を置き、frontmatter に `okf_version: "0.2"`、本文にすべてのコンセプトの一覧を書く（SPEC §8、§12）。
  コンセプトを足す・消す・`title` や `description` を変えたときは、`index.md` も直す。
- `log.md` は置かない。更新の履歴は git で追う。

OKF から外れる点は次のとおり。どれも OKF の適合条件（SPEC §11）には反しない。

- 出典は frontmatter の `sources` と脚注 `[^id]`（SPEC §5.1）ではなく、本文の番号と `## 出典` の一覧で書く（「出典」節）。
- リンクは、OKF が推奨するバンドル基準の絶対パス（`/status/attack.md`）ではなく、相対パスで書く。
  バンドルがリポジトリの部分ディレクトリなので、絶対パスは GitHub 上でリポジトリの root 基準になり、リンクが切れるため。

## 置くもの・置かないもの

ナレッジに置くのは、ゲームの振る舞いと、アイテムデータなどの外部データの性質である。ff11sim をどう作るかは置かない。

| 書きたいこと | 置き場 |
|---|---|
| ゲームの計算式・仕様・データの性質 | `docs/internal/knowledge/` |
| ff11sim が何をどう計算・表示するか、何を計算しないか | 仕様書（`docs/internal/specs/`） |
| 設計判断とその理由 | ADR（`docs/internal/adr/`） |
| ナレッジと実装の食い違い、ゲームにはあるが計算していないもの | tech-debt（`docs/internal/tech-debt/`） |

コードの関数名・ファイルの行番号・計算していない項目の一覧は、実装が変わると古びるのでナレッジに書かない。
ナレッジとコードの対応は、末尾の「ff11sim での扱い」に仕様書・ADR・コードへのリンクとして置く。

## ファイルの形

```markdown
---
type: Formula
title: "攻撃力 (Attack)"
description: "メイン・サブ・遠隔の攻撃力のうち、加算で求める部分（加算枠）の式。"
status: draft
---

# 攻撃力 (Attack)

このファイルが何を記録するかを 1〜2 文で書く。関係するナレッジへのリンクもここに置く。

## （本文。見出しは題材に合わせて自由に決める）

主張の末尾に出典の番号を付ける [1]。

## 計算例

## ff11sim での扱い

## 未確認の事項

## 出典

1. [攻撃力 - FF11用語辞典](https://wiki.ffo.jp/html/1766.html) — 有志の辞典
```

- **frontmatter**: 次の 4 つのキーを書く。

| キー | 書くこと |
|---|---|
| `type` | 内容の種類。次の 3 つのどれか。`Formula`（計算式）、`Game Rule`（ゲームの規則・値の表）、`Data Property`（アイテムデータなど外部データの性質）。題材はディレクトリで分かるので、`type` は「どう読む文書か」を表す |
| `title` | 本文の `# タイトル` と同じ文字列 |
| `description` | このファイルが何を記録するかを 1 文で。`index.md` の一覧にもそのまま載せる |
| `status` | `## 未確認の事項` が「なし」でなければ `draft`。「なし」なら `stable`（SPEC §5.4） |

  OKF の `verified`（誰がいつ出典と照合したか、SPEC §5.2）は使わない。確認状態は `status` と `## 未確認の事項` で表す。
- **タイトル**: 題材の名詞句。英語名があれば括弧で添える。「計算仕様」などの接尾辞は付けない。
- **冒頭の文**: このファイルが何を記録するかを 1〜2 文で書く。
- **本文**: 見出しは題材に合わせて自由に決める。ただし、他の文書から「〇〇」節として参照されている見出しは、
  参照元も直さない限り名前を変えない。
- **末尾の節**: 次の順に置く。

| 節 | 必須か | 書くこと |
|---|---|---|
| `## 計算例` | 式を扱うときだけ | 具体的な入力と、式に当てはめた途中の値と結果 |
| `## ff11sim での扱い` | 必須 | 対応する仕様書・ADR・tech-debt・コードへのリンクを数行。ff11sim が計算に使っていないときはそう書く |
| `## 未確認の事項` | 必須 | 照合できていない主張。無ければ「なし」と書く |
| `## 出典` | 必須 | 番号付きの一覧 |

## 出典

本文の主張の末尾に `[1]` のように番号を付け、末尾の `## 出典` に同じ番号で一覧を置く。

- 1 つの主張が複数の出典に基づくときは `[1][2]` と並べる。
- 一覧の各項目は「リンクかタイトル（日付）— 種別」の形で書く。日付は、出典に書かれた日付か、出典を確かめた日付。
- 番号は本文に初めて出る順に振る。出典を足したり消したりしたら振り直す。
- 出典を持たない主張を本文に残すときは、番号を付けず、「未確認の事項」にその主張を挙げる。

### 出典の種別

| 種別 | 意味 | 例 |
|---|---|---|
| 公式 | スクウェア・エニックスが出した資料 | バージョンアップ情報、公式フォーラムの開発者の投稿 |
| 有志の辞典 | 有志が運営する wiki・辞典 | [FF11用語辞典](https://wiki.ffo.jp/)、[BG Wiki](https://www.bg-wiki.com/) |
| 有志の検証 | 個人が実測・解析して公開した結果 | X（旧 Twitter）の検証スレッド、ブログ |
| データの集計 | アイテムデータなどの外部データを数えた・調べた結果 | `build/items.json` を数えた件数 |
| ユーザーの確認 | ユーザーがゲーム内で確かめた結果 | ユーザーの言葉をそのまま引用する |
| ユーザーの判断 | ゲームでは確かめず、ユーザーが決めた扱い | 仕様書の grill で決めた規則 |

「ユーザーの判断」に基づく主張は、ゲームの一次情報で確かめていないので、必ず「未確認の事項」にも書く。

## 未確認の事項

照合できていない主張を箇条書きにする。何を何と照合していないかを書く。

- 良い例: 「rank4・rank5 の内部値は [1] だけに基づき、ほかの出典と照合していない。」
- 悪い例: 「一部未確認。」（どの主張か分からない）

## 文体

読者が読み返さずに論理を追えることを優先する。

- 体言止めと箇条書きだけで済ませず、主語と述語のある文で書く。
- 比較を含む語（「異なり」「大きい」など）では、何と何を比べたかを書く。
- 新しい語や略語（ジョブの略称、JP など）は初出で定義するか、[用語集](../../CONTEXT.md) の語を使う。

式はコードブロックに書き、式に出てくる項を表か文で説明する。

## ファイルの置き場

`docs/internal/knowledge/` の下に、題材ごとのディレクトリを置く。

| ディレクトリ | 題材 |
|---|---|
| `status/` | キャラクターのステータスとその計算式 |
| `job_traits/` | ジョブ特性 |
| `items/` | アイテム・装備とアイテムデータの性質 |

題材がどれにも合わないときは、新しいディレクトリを作ってこの表と `index.md` の節に足す。
