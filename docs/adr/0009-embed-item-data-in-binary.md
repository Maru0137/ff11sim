# 0009. 装備データを WASM バイナリに埋め込む

## Context and Problem Statement

`items.json` は上流から生成する 8.5MB の派生物で、現在は `web/data/` に置かれ
GitHub Pages から配信されている（[ADR 0003](0003-items-json-generated-in-ci.md)）。
読み手は JavaScript だけであり、Rust からは参照できない。

そのため [ADR 0001](0001-rust-wasm-static-site.md) の 3 番目のドライバ
「同じコア実装を CLI やスクリプトからも実行し、一括シミュレーションに使えること」が
実現できない。装備の組み合わせを探索するようなシミュレーションは、装備データに
アクセスできない現状の Rust では書けない。また `rust/src/wasm.rs` のテストは装備の数値を
人間の手で書き写しており、上流データが更新されると黙って実態とずれる。

装備データをどこに置くかを決める必要がある。ここで決まる配置が、解釈（説明文から数値を
取り出す処理）をどちらの言語に置けるかを規定するため、先に決める。

## Decision Drivers

* Rust（ネイティブ CLI と WASM の双方）から装備データを扱えること
* 利用者の転送量を増やさないこと
* キャッシュの粒度を大きく損なわないこと
* チェックアウト直後に `cargo test` が通ること（ビルド順の制約を持ち込まないこと）
* [ADR 0003](0003-items-json-generated-in-ci.md) の「`items.json` は git 管理外」と
  両立すること

## Considered Options

1. 配信物のまま据え置く
    - 1.1. Rust からは扱えないままとし、一括シミュレーションは Node スクリプトで行う
    - 1.2. 呼び出し側が読み込んで Rust に渡す（コアは I/O を持たない）
2. WASM バイナリに埋め込む
    - 2.1. 全ビルドに埋め込み、JS 側の読み込みを廃止する
    - 2.2. ネイティブビルドにだけ埋め込む

1 は「データは配信物のまま」、2 は「データをバイナリに入れる」で分かれる。

## Decision Outcome

選択: **2 + 2.1. 全ビルドに埋め込み、JS 側の `items.json` 読み込みを廃止する**（採用）。

決め手は、gzip 後の転送量が現状とほぼ変わらないという実測である。データを埋め込んだ
wasm は 8,558,576 バイト（gzip 1,133,776）で、ラッパのオーバーヘッドは raw 440 バイト・
gzip 473 バイトしかない。現状（`items.json` gzip 1,133,303 + `ff11sim_bg.wasm` gzip
49,441 = 1,182,744）との差は 1KB 未満である。利用者の体感コストが増えないなら、
Rust が装備データを直接扱える利益を取れる。

- `items.json` は `scripts/build_web_data.sh` が生成し、`include_str!` で埋め込む。
  ビルド順は **データ生成 → `cargo test` → `wasm-pack build`** となる。
  CI のステップ順を入れ替え、README にもローカルでの前提として明記する。
- **`items.json` の位置づけを「Web の配信物」から「ビルドの中間生成物」に変える。**
  `web/data/` に置いたままだと Pages に配信されて同じデータを二重に配ることになるため、
  配信対象外の場所へ出力する。
- JS 側は `items.json` を fetch しない。装備の参照は WASM 経由にする。
  これに伴って解釈をどう移すかは [ADR 0010](0010-equipment-interpretation-in-rust.md)
  で決める。
- `augments.json`（284KB、リポジトリ管理下）も同様に埋め込む。こちらは git にあるので
  ビルド順の制約を受けない。
- Rust のテストは埋め込んだ実データをアイテム ID で引けるようになるため、
  `rust/src/wasm.rs` が doc comment に手書きしている装備の数値は不要になる。

### この決定を見直す条件

- キャッシュ粒度の悪化が実際に問題として観測されたとき。その場合は 1.2
  （呼び出し側が渡す）へ移り、データを別ファイルに戻す。コアの API を
  「データを引数で受け取る」形にしておけば、この移行は局所で済む。
- 初回ロードの体感が問題になったとき。移植完了時点の実測は gzip 約 1.5MB
  （移植前比 +34%）で、2026-08-10 時点では許容と判断している。回線が細い環境からの
  利用が増えるなど前提が変われば、まず解釈側のサイズ削減を検討する。

### Consequences

* Good: Rust が装備データを直接扱えるようになり、
  [ADR 0001](0001-rust-wasm-static-site.md) の 3 番目のドライバを正面から満たす。
  `main.rs` と `clap` 依存の位置づけも定まる。
* ~~Good: 転送量は現状と実質同じ（gzip で差 1KB 未満）。~~
  → **実測では +34% (gzip +402KB) だった。** 解釈の移植で正規表現エンジンが
  乗るぶんを見込めていなかった。詳細は Confirmation を参照。
* Good: 配布物からデータファイルが 1 つ消え、データとコードのバージョンずれが
  原理的に起きなくなる。
* Good: `rust/src/wasm.rs` の手書き転記が不要になり、上流更新による静かな乖離が消える。
* Bad: **キャッシュ粒度が悪化する。** 現在はコード変更なら wasm の gzip 49KB、
  データ更新なら `items.json` の 1.08MB と、変更した側だけが再取得される。
  埋め込むと 1 つの成果物になるため、どちらの変更でも利用者に 1.18MB を再取得させる。
  デプロイは push のたびに走るので、日常的に効く。
* Bad: `cargo build` の前にデータ生成が必須になる。チェックアウト直後の `cargo test` が
  コンパイルエラーで落ち、Rust だけを触りたい場合にも上流データの取得を強いる。
  4 番目のドライバを満たせていない。
* Bad: JS がデータを読めなくなるため、解釈も Rust に移さざるを得ない。
  移植コストは [ADR 0010](0010-equipment-interpretation-in-rust.md) が負う。
* Neutral: WASM のリニアメモリに 8.5MB の文字列とパース後の構造が載る。
  現在も JS 側が同等以上を保持しているため、総量として悪化するとは限らない（未計測）。

### Confirmation

**実装完了後の実測 (2026-08-10)**

決定の決め手だった「転送量はほぼ変わらない (差 1KB 未満)」は **成立しなかった**。

| | gzip |
|---|---|
| 移植前 (`items.json` + 旧 wasm) | 1,182,733 |
| 移植後 (wasm + `augments.json`) | 約 1,585,000 |
| 差分 | **+402,000 (+34%)** |

内訳は正規表現エンジンが約 +339KB、残りが埋め込みのオーバーヘッド。
事前計測ではパターン 1 本の試験クレートで測っていたが、実際は 80 以上のパターンを
コンパイル済みで保持するため乖離した。また `cargo build --target wasm32` の生成物は
wasm-bindgen 処理前で既存 export すら含まないため、測定は `wasm-pack` 経由で
行う必要がある (当初この点も誤っていた)。

**この +34% は許容する (2026-08-10 判断)。** 移植後の実物をブラウザで触って
体験に遜色がないことを確認したうえでの判断。絶対値では gzip 約 1.5MB で、
初回ロード後はキャッシュが効く。サイズ削減の作業コストに見合う効果が
現時点では見込めない。

削減が必要になったときの対象は [ADR 0010](0010-equipment-interpretation-in-rust.md)
の解釈側になる。正規表現の遅延コンパイル (使うパターンだけ組み立てる) か、
手書きパーサ化で regex エンジンごと落とす方向。後者は移植をやり直すことになる。

**以下は決定時点の計測**

計測済み:

* データを埋め込んだ wasm のサイズ: 8,558,576 バイト / gzip 1,133,776 バイト。
  ラッパのオーバーヘッドは raw 440 バイト・gzip 473 バイト。
* 8.6MB を埋め込んだネイティブのクリーンビルド: 0.68 秒。コンパイル時間は問題にならない。
* 現状の配信量: `items.json` gzip 1,133,303 バイト + `ff11sim_bg.wasm` gzip 49,441 バイト。

**実装完了時の確認 (2026-08-10)**

* `items.json` の出力先を `build/` に移し、Pages の配信物から外した。
  `deploy.yml` の `upload-pages-artifact` は `path: './web'` なので `build/` は入らない。
  実測で配信量が gzip 約 2,750,000 → 1,633,087 バイトに減り、
  `items.json` ぶん (gzip 約 1,133,000) が消えたことを確認した。
* CI のステップ順を「データ生成 → `cargo test` → `wasm-pack build`」に入れ替えた。
* `web/README.md` にチェックアウト直後の手順を明記した。
* `items.json` は配信されないが、CI が `items-json` という artifact として
  実行ごとに残す (保持 30 日)。公開後に中身を確認したいときはここから取得する。
  `_build_metadata.json` の `commit` で該当の実行を特定できる。
* 上流に変化が無いときは生成をやり直さない。生成元の指紋 (上流 blob SHA +
  変換スクリプトのハッシュ) を `build/.items-signature` に記録し、CI では
  `actions/cache` のキーにも使う。`workflow_dispatch` では必ず作り直す。

未確認:

* CI 上でのキャッシュヒットは未確認。`actions/cache` の挙動はローカルで再現できない。
  初回実行は必ずミスし、2 回目以降のログで `Build web data` が
  「items.json は最新のため再生成をスキップ」と出れば期待どおり。

## Pros and Cons of the Options

### 1. 配信物のまま据え置く

* Good: 現在のキャッシュ粒度を保てる。コード変更とデータ更新が独立して再取得される。
* Good: `cargo build` にデータ生成の前提が入らない。
* Bad: 配信物とバイナリにデータが分かれるため、両者のバージョンずれが起こりうる。

#### 1.1. Rust からは扱えないままとし、一括シミュレーションは Node スクリプトで行う

* Good: コストゼロ。既存の境界を一切触らない。
* Good: [ADR 0001](0001-rust-wasm-static-site.md) のドライバは「CLI **やスクリプト**から」と
  書いており、Node スクリプトが WASM を呼べば同じコア実装が実行される。
  文言としては 3 番目のドライバを満たす。
* Bad: Rust は装備を知らないままで、`rust/src/wasm.rs` の手書き転記が残る。
  上流更新のたびに黙って腐り続ける。
* Bad: 装備解釈に Rust の型の恩恵が及ばない。
* Bad: Node から `web/pkg` の WASM を読む方法の確認が要る。現在のビルドは
  `wasm-pack --target web` でブラウザ向けであり、`--target nodejs` での追加ビルドか
  `init` にバイト列を渡す実装が必要（未検証）。

#### 1.2. 呼び出し側が読み込んで Rust に渡す

* Good: コアが I/O を持たないままで、[ADR 0001](0001-rust-wasm-static-site.md) の
  「コアは実行形態に依存しない」と整合する。ネイティブは `std::fs`、WASM は JS が渡す。
* Good: `cargo build` 前のデータ生成を強制しない。チェックアウト直後でも
  `cargo test` がそのまま通る（2.x との決定的な差）。
* Good: WASM のサイズが増えず、キャッシュ粒度も保たれる。
* Bad: WASM 側では JS が読み込んだデータを境界越しに渡すことになり、
  メモリが二重に消費される。8.5MB のデシリアライズコストもかかる。
* Bad: 呼び出し側にデータ読み込みの責務が生じ、CLI・WASM の双方で配線が要る。

### 2. WASM バイナリに埋め込む（採用）

`items.json` がリポジトリに無くても、`include_str!` はコンパイル時に存在すればよい。
`scripts/build_web_data.sh` を `cargo build` より前に走らせれば成立し、
[ADR 0003](0003-items-json-generated-in-ci.md) の git 管理外方針とは矛盾しない。

* Good: Rust が単体で完結し、呼び出し側の準備が要らない。
* Good: コンパイル時間は問題にならない（実測 0.68 秒）。
* Bad: `cargo build` の前にデータ生成が必須になる。
* Bad: キャッシュ粒度が悪化する。

#### 2.1. 全ビルドに埋め込み、JS 側の読み込みを廃止する（採用）

データが WASM に入る以上、JS 側は `items.json` を読まない。読み込みを残すと
同じデータを二重に配ることになるため、この 2 つはセットでしか成立しない。

* ~~Good: **転送量は現状とほぼ変わらない**（gzip で差 1KB 未満）。~~
  → データ埋め込み単体ではそのとおりだったが、解釈の移植に伴う正規表現エンジンで
  最終的に +34% になった。実測値は Confirmation を参照。
* Good: ブラウザとネイティブで同じデータ・同じコードパスになり、
  `cargo test` の検証範囲が WASM にもそのまま及ぶ。
* Bad: JS がデータを読めなくなるため、解釈と検索を Rust に移す必要が生じる
  （[ADR 0010](0010-equipment-interpretation-in-rust.md)）。
* Bad: `web/test/*.test.js` は `items.json` を直接読んでいるため作り直しが要る。

#### 2.2. ネイティブビルドにだけ埋め込む

`#[cfg(not(target_arch = "wasm32"))]` で埋め込みをネイティブ限定にする。
装備データを必要とするのは一括シミュレーション（CLI）だけ、という判断。

* Good: ブラウザ側は現状のまま変わらない。解釈の移植もキャッシュ粒度の悪化も起きない。
* Bad: 同じコアがターゲットによって「装備を知っている / 知らない」と挙動が分かれる。
  [ADR 0001](0001-rust-wasm-static-site.md) が置いた「コアは実行形態に依存しない」
  という制約の趣旨に反する。WASM で通らないコードパスが生まれ、
  `cargo test` がネイティブでしか検証しない領域を作る。
* Bad: `cargo build` 前のデータ生成が必要な点は 2.1 と変わらない。
