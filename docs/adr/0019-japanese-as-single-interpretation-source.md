# 0019. 装備解釈の入力を日本語説明文に一本化し、条件ラベルの規則を共有する

## Context and Problem Statement

[ADR 0018](0018-equip-module-owns-interpretation.md) で装備の解釈は `equip` / `equip_stats`
に集約したが、**解釈の経路が 2 本あり、同じ装備から違う値が出る**状態は残っている。

| | 経路 A（ステータス計算） | 経路 B（ユーザー定義プロパティ） |
| --- | --- | --- |
| アイテム | `description_en` | `description_ja` |
| オグメント / カスタム説明 | JA→EN 変換を通す | 日本語のまま |
| 抽出 | 固定 78 項目・全一致合算 | 任意名・最初の一致のみ |
| 条件セグメント | `Pet` / `Avatar` / `Wyvern` / `Automaton` のみ除去、**残りは全部加算** | **全部除外** |

食い違いの原因は 2 つある。

1. **読むテキストが違う**。オグメント / カスタム説明は元が日本語で、経路 A のためだけに
   JA→EN 変換（`convert_augment_ja_to_en`、88 件の置換表）を通している。この表は
   オグメント文向けの語彙しか持たないため、表に無い語は経路 A だけが取りこぼす。
2. **条件セグメントの扱いが違う**。経路 A は `コンビネーション:` `ユニティランク:`
   `潜在能力:` などを無条件に加算し、経路 B は除外する
   （[docs/knowledge/items/description_labels.md](../knowledge/items/description_labels.md)）。

計測（2026-08-15、全 15,452 件）: `description_ja` を現在の変換表に通して抽出すると、
`description_en` からの抽出と **13,164 件で食い違う**。内訳は語彙の欠落が支配的で、
`防` 8,283 件 / `Ｄ`・`隔` 各 4,565 件 / `魔防` 2,674 件 / `敵対心` 1,560 件 /
武器・防御スキル 19 種 / `ファストキャスト` `リフレシュ` `リジェネ` `スナップショット` など。
いずれも**表に無いだけ**で、変換が誤っているわけではない。

どちらの言語を解釈の入力にするか、条件セグメントの規則を共有するかを決める必要がある。

## Decision Drivers

* 同じ装備・同じ項目なら、どちらの経路でも同じ値が出ること
* 装備の解釈が参照するテキストが 1 つであること（[ADR 0018](0018-equip-module-owns-interpretation.md)
  の「解釈は 1 箇所」をデータ面でも満たす）
* ユーザー定義プロパティは任意の日本語プロパティ名を扱う。原理的に英語へ寄せられない
  （[ADR 0015](0015-property-sets.md)）
* 移行の正しさを機械的に検証できること。JS リファレンスは削除済みで、いま検証に使えるのは
  現行の英語経路だけ（[ADR 0018](0018-equip-module-owns-interpretation.md) の Confirmation）
* 移植量が個人開発として現実的であること

## Considered Options

1. 現状維持。2 経路の食い違いを許容する
2. 英語に統一する
3. 日本語に統一する
    - 3.1. 表記の正規化層（現 `convert_augment_ja_to_en`）を拡充し、既存の抽出器に流す
    - 3.2. 日本語語彙の抽出器を新規に実装し、英語の抽出器を捨てる

選択肢 2 と 3 は「どちらの言語を入力にするか」で分かれる。3.1 と 3.2 は
「既存の抽出器（78 項目 × 59 正規表現、手書きテスト 33 件）を活かすか捨てるか」で分かれる。

条件セグメントの扱いは上記と直交する別の軸だが、**規則を共有しない限り食い違いは消えない**ため
本 ADR で併せて決める。

## Decision Outcome

選択: **3.1. 日本語に統一し、表記の正規化層を拡充する**（採用）。
条件ラベルの規則は両経路で共有し、**コンビネーションだけ常時扱いとして加算する**。

**統一するのは「読む対象のテキスト」と「どのセグメントを読むか」であって、抽出器そのものではない。**
経路 A は固定 78 項目を全一致合算し、経路 B は任意名を最初の 1 件だけ取る。この違いは
用途から来る仕様であって、揃えるべきものではない。

**パイプライン**

```
description_ja / オグメント文 / カスタム説明 (すべて日本語)
  ↓ 条件ラベル配下を除去 (コンビネーションは残す。両経路共通)
  ├─ 経路 A: 表記の正規化 (日本語表記・略記 → 正規表記) → 固定 78 項目を抽出
  └─ 経路 B: そのまま → 任意名を 1 件抽出
```

- `description_en` は解釈に使わない。検索の説明文ステータスソートで
  `description_ja` が無い場合のフォールバックとしてのみ残る。
- 現 `convert_augment_ja_to_en` は「オグメントの日本語表記を英語に翻訳するもの」ではなく
  **「表記ゆれを抽出器が読める正規表記に寄せる正規化層」**として位置づけ直す。
  正規表記がたまたま英語なのは、抽出器が英語説明文からの移植
  （[ADR 0010](0010-equipment-interpretation-in-rust.md)）だからにすぎない。
- 条件ラベルの判定と除去は 1 箇所に置き、両経路が同じ関数を通る。
  除去の範囲は**ソースによって変える**（2026-08-15 改訂。当初は全ソース「行末まで」だった）。
  アイテム説明文の改行はゲーム内表示の折り返しなので「次のラベルかテキスト末尾まで」、
  オグメント文とカスタム説明の改行は効果 1 件ごとの区切りなので「行末まで」
  （[docs/knowledge/items/description_labels.md](../knowledge/items/description_labels.md)）。
  ソースごとに違うのは規則の分岐ではなく、同じ規則（ラベルは以降に及ぶ）を
  改行の意味が違う入力に当てはめた結果。
- **コンビネーションは例外として加算する。** 本ツールは装備セットを組むためのもので、
  セット効果は実際には発動していることが多いため。これは経路 B の現在の挙動を変える
  （[ADR 0015](0015-property-sets.md) の 2026-08-14 の追加分を一部撤回する）。
  他のラベル（潜在能力 / エンチャント / アフターマス / ユニティランク / エリア・時間・天候 /
  ペット系）は両経路で除外する。

**移行の順序**

各段階でテストが通る状態を保つ。

1. 正規化層を拡充する。`extract_all_stats(正規化(description_ja))` と
   `extract_all_stats(description_en)` の差を測り、**日本語側の誤変換を潰す**。
   残る差は分類して記録する（この段階では経路 A の入力は `description_en` のままなので、
   アイテム説明文の解釈は変わらない。オグメント / カスタム説明の解釈は語彙が増えるぶん
   改善する = 今まで取りこぼしていた表記が拾えるようになる）
2. 経路 A の入力を `description_ja` に切り替える。手順 1 で分類した 302 件については
   値が変わる（多くは日本語側の方が正しい方向への変化）。それ以外は変わらない
3. 条件ラベルの除去を両経路の共通処理にし、コンビネーションを例外にする。
   ここで初めて表示値が変わる（潜在能力・ユニティランクなどが外れ、
   経路 B ではコンビネーションが乗るようになる）
4. 英語説明文専用になっていた前処理（属性アイコン展開、`Pet:` セグメント除去、
   Unity Ranking の範囲最大値取り）の位置づけを整理する。**削除はしない**:
   `extract_all_stats(description_en)` は手順 1 で作った全件比較の参照側であり、
   前処理を消すと参照が変質して比較にならなくなる。日本語経路からは条件ラベルが
   前段で落ちるので到達しない、とモジュールの doc に明記するにとどめる

### Consequences

* Good: 同じ装備・同じ項目なら経路 A と B が同じ値を返す。ユーザーから見た最大の不整合が消える。
* Good: 解釈が参照するテキストが `description_ja` 1 つになる。オグメント / カスタム説明と
  アイテム説明文が同じ扱いになり、「アイテムだけ英語で読む」という非対称が無くなる。
* Good: 正規化層の欠落が経路 A だけの取りこぼしを生む構造が無くなる。
  語彙を足せば両経路が同時に改善する。
* Good: 手順 1 の全件比較は、削除された JS リファレンスの代わりになる検証資産として残せる
  （Confirmation 参照）。
* Good: 比較の過程で、**日本語側の方が正しい箇所が多数あることが分かった**。英語説明文の
  解釈は `Breath Damage taken` を汎用の被ダメージとして数える、
  `Dark Elemental Magic Attack` の `Attack` を攻撃力として数える、
  `"Spirit Jump" attack +17%` を攻撃力% として数えるといった過剰マッチを持つ。
  日本語表記はこれらを別語として書き分けているため、同じ取り違えが起きない。
  日本語への一本化はこれらの誤りの解消も兼ねる。
* Bad: 手順 3 で表示値が下がる装備が出る。潜在能力 383 件・アフターマス 341 件・
  エンチャント 423 件・ユニティランク 217 件などの条件付き効果が加算されなくなる。
  これは「常時発動でないものを常時として数えていた」誤りの是正だが、
  利用者から見れば値の変化になる。
* Bad: 正規化層は順次置換なので、装備説明文全体に適用すると短いオグメント文よりも
  衝突の危険が上がる（長い表記を先に置く順序への依存が強まる）。実際に
  「使用間隔」の「隔」が `Delay:` に、「属性魔攻」が汎用の魔攻に誤爆した。
  英語経路との全件比較で検出して潰した。
* Bad: コンビネーションだけを例外にするのは、厳密には「セット装備数の条件を無視している」
  ことに変わりはない。条件ごとの発動状態を扱うなら別途 UI が要る（More Information）。
* Neutral: 抽出器そのものは統一しない。経路 A（固定 78 項目・全一致合算）と
  経路 B（任意名・最初の 1 件）の違いは用途から来る仕様として残す。
* Neutral: `description_en` はデータとしては残る。検索のフォールバックと、
  英語名での装備検索に引き続き使う。

### Confirmation

* `cargo test` — `rust/tests/ja_en_conformance.rs`。全装備について実際のパイプライン
  （条件ラベル除去 → 正規化 → 抽出）の結果を `extract_all_stats(description_en)` と
  突き合わせる。`--nocapture` で項目別の内訳と実例が出る。

  **完全一致も、件数の固定も目標にしない。** 差 1,467 件を次のように分類し、
  **分類できない差の件数だけ**を見る（実測 94 件、上限 150 件）。

  | 分類 | 件数 | 判定方法 |
  | --- | --- | --- |
  | 条件セグメントの扱い | 1,271 | `strip_conditional_labels` が何か落としたか |
  | 英語側の癖・表記ゆれ | 102 | 英語説明文に既知の目印があるか（`EN_QUIRK_MARKERS`） |
  | データ差 | 94 | 上記以外。日本語と英語で数値自体が違う装備 |

  件数を上限にする方式は最初に試して失敗した。CI は items.json を上流から再生成する
  ため、手元 15,452 件 / CI 15,473 件と中身がずれ、総数 2 件の差で落ちた。
  分類方式なら、条件ラベル付きの装備が増えても自動的に分類される。

  分類できない差が増えたら、正規化層の語彙が抜けたか、英語側の新しい癖が現れたか、
  データ差が増えたかのいずれか。内訳を見て `AUGMENT_JA_TO_EN` か
  `EN_QUIRK_MARKERS` に足す。

  **期待値 JSON への凍結は行わない。** この全件比較自体が回帰検出として機能しており、
  参照が現物の英語説明文なので凍結ファイルより情報量が多いため。debug ビルドで
  約 105 秒かかるのが難点で、CI 時間が約 4 分 → 約 6 分に伸びる。
* `cargo test` — `rust/src/equip.rs` / `rust/src/equip_stats.rs` の既存テスト
  （[ADR 0018](0018-equip-module-owns-interpretation.md) の Confirmation を参照）。
  手順 3 では条件ラベルのテストを、コンビネーションが加算される期待値に更新する。
* `npm run test:unit` — `web/src/equip/equip-bonuses.test.ts` と
  `web/src/propsets/user-item-values.test.ts`。WASM 境界を通した結果が変わらないこと
  （手順 1・2）と、手順 3 の挙動変更が意図どおりであることを検証する。
* `npm run test:smoke` — 装備セットの編集・保存とステータス表示の通し。

検証されていないもの:

* 手順 3 の挙動変更が「実際のゲームでの値」と合っているかは検証できない。
  条件付き効果を常時として数えないという方針判断であり、正解データは無い。
* コンビネーションを常時扱いにする判断も同様。セット装備数の条件は見ていない。

## Pros and Cons of the Options

### 1. 現状維持

* Good: コストゼロ。
* Bad: 同じ装備でステータス表示とユーザー定義プロパティが違う値を出す状態が残る。
* Bad: 語彙を足すときに 2 経路それぞれの都合を考える必要が残る。

### 2. 英語に統一する

* Good: 既存の抽出器と 33 件の手書きテストがそのまま活きる。アイテム説明文の解釈も変わらない。
* Bad: **ユーザー定義プロパティが成立しない。** 任意の日本語プロパティ名を英語に変換するには
  変換表に全語彙が必要で、ユーザーが自由に定義する語はそもそも表に載らない
  （[ADR 0015](0015-property-sets.md) が日本語のまま扱うと決めた理由）。
* Bad: オグメント / カスタム説明は元が日本語なので、変換層は結局残る。

### 3. 日本語に統一する（採用）

* Good: 原文が日本語のソース（オグメント / カスタム説明）に変換を挟まなくてよくなる。
* Good: ユーザー定義プロパティと同じテキストを読むので、食い違いの原因が構造的に消える。
* Bad: アイテム説明文の解釈が変換層に依存するようになる。現在は英語を直接読んでいて正確。

#### 3.1. 正規化層を拡充する（採用）

* Good: 既存の抽出器（78 項目 × 59 正規表現）と手書きテスト 33 件を維持できる。
* Good: 追加するのは語彙エントリで、作業が機械的。英語経路との全件比較で進捗を測れる
  （13,164 件の差 → 302 件まで縮んだ）。
* Bad: 「日本語を正規表記に直してから読む」という 2 段構えが残る。
  正規表記が英語なので、パイプラインの見た目が不自然に映る。
* Bad: 順次置換の衝突リスクが装備説明文全体に広がる。

#### 3.2. 日本語語彙の抽出器を新規実装する

* Good: パイプラインが素直になる。日本語を日本語のまま読む。
* Good: 日本語表記の方が構造が規則的（`防22 命中+8`。コロン付きラベルは必ず条件）。
* Bad: 78 項目 + スキル 33 種のパターンを書き直す必要があり、量が桁違いに大きい。
* Bad: 既存の手書きテスト 33 件と、移植で作り込んだ細かい挙動を捨てることになる。
* Bad: 検証に使えるオラクルは結局現行の英語経路なので、3.1 と同じ全件一致作業が
  そのうえ**さらに**必要になる。
