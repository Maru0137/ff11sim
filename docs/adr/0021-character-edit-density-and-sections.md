# 0021. キャラクター編集フォームを開閉式 5 セクションに再編し、入力欄の幅を値の桁数で決める

## Context and Problem Statement

キャラクター編集フォームは 7 セクションを常時展開し、143 個の数値入力を縦に並べていた
（ジョブレベル 22×2、メリット基礎 9、メリットスキル 33、メリットその他 5、
ジョブ別メリット最大 16、JP 10、スキル値 33）。実測でフォーム高さは 3,913px。
横方向も、`.merit-grid` / `.skill-grid` が 3 列固定、`.jp-grid` が 2 列固定のところに
`input { width: 100% }` を敷いていたため、2 桁の値の入力欄が 332〜503px を占めていた
（フォーム欄 1046px 時。本番は `.content-wrap` が最大 1600px なのでさらに広い）。

「1 箇所だけ直したい」ときの移動量と、幅の使われ方を改善する必要がある。
決めるべきは (a) 幅と情報密度の詰め方、(b) 縦の長さの畳み方、(c) セクションの束ね方、
(d) ジョブ別メリットと JP のジョブ選択の扱い、(e) 上限を超える入力の扱い、
(f) 上限 0 のスキル欄の見せ方、(g) 数値欄の編集開始時の挙動。

## Decision Drivers

* 入力欄の幅が「入る値」に見合っていること（2 桁の値に数百 px を割り当てない）
* 画面幅が変わっても列数が追従すること（3 列固定だと広い画面で余り、狭い画面で溢れる）
* 既存編集（1 箇所だけ直す）で端から端まで移動しなくて済むこと
* 新規作成（全項目を設定する）の動線を壊さないこと
* 入力できる値の範囲が、その欄を見れば分かること
* ゲーム仕様上あり得ない値は、警告ではなく入力させないこと
* 既に保存されているデータを、読み込んだだけで書き換えないこと

## Considered Options

1. 幅と情報密度の詰め方
    - 1.1. 列数は固定のまま、入力欄だけ狭める
    - 1.2. `repeat(auto-fill, minmax(...))` で列数を幅に追従させ、ラベルを入力と同じ行に置く
2. 縦の長さの畳み方
    - 2.1. 全セクション展開のまま（1.2 の密度改善だけで済ませる）
    - 2.2. 装備セット画面と同じサブタブに分割する
    - 2.3. `<details>` の開閉式にし、畳んだ状態にも要約を出す
3. セクションの束ね方
    - 3.1. 7 セクションのまま
    - 3.2. メリット 3 種を「メリットポイント (共通)」に、ジョブ別メリットと JP を
      「ジョブ別ポイント」に束ねて 5 セクションにする
4. ジョブ別メリットと JP のジョブ選択
    - 4.1. `jmJob` / `jpJob` の 2 つを維持する
    - 4.2. 1 つに統合し、セクション先頭に置く
5. 上限を超える入力の扱い
    - 5.1. 入力は許して超過を警告表示する
    - 5.2. 入力時に上限でクランプする
        - 5.2.1. 加えて読み込み時にも一括クランプする
        - 5.2.2. 保存済みの超過値はその欄を触るまで温存する
6. 上限 0 のスキル欄
    - 6.1. 他と同じように表示する
    - 6.2. `disabled` にする
    - 6.3. 畳んで「上限 0 のスキル N 件」で開けるようにする
7. 数値欄の編集開始時の挙動
    - 7.1. 何もしない（既定値を消してから打ち直す）
    - 7.2. フォーカスで全選択する
    - 7.3. フォーカスで中身を消す

1〜3 はレイアウトの決定、4〜7 は入力挙動の決定で、独立に選べる。

## Decision Outcome

選択: **1.2 + 2.3 + 3.2 + 4.2 + 5.2.2 + 6.2 + 7.2**。

- **入力欄の幅**: `#charEditSection input[type="number"]` を 62px 固定・右寄せにし、
  スピナーは隠す（`appearance: textfield`。幅を食うだけで、↑↓ キーは引き続き効く）。
  名前は 280px、種族セレクトは 200px を上限にし、2 つを 1 行に並べる。
- **列数**: `.merit-grid` / `.jp-grid` / `.skill-grid` を
  `repeat(auto-fill, minmax(var(--col-min), 1fr))` にし、ラベル長に応じて
  `--col-min` を指定する（メリット 175px / メリットその他 255px /
  ジョブ別メリット・JP 275px / スキル値 200px）。
- **1 項目 1 行**: `.merit-item` / `.jp-item` / `.skill-item` を横並びにし、
  `ラベル … 入力 / 最大値` を 1 行に収める。全項目で分母（`/ 最大値`）を出し、
  上限に達した欄は分母を青字（`.at-cap`）にする。上限 0 は「達成」ではないので付けない。
- **ジョブレベル**: 22 行のテーブルをやめ、`[ジョブ名][Lv][ML]` のチップ グリッドにする。
  全 22 ジョブを常に表示する（新規作成時は全ジョブ Lv99 が既定なので絞り込みは意味を持たない）。
  Lv1 以上のジョブはジョブ名を明るくするだけに留め、畳んだときの要約は出さない。
- **セクション**: `<details>` の 5 セクション（基本情報 / ジョブレベル /
  メリットポイント (共通) / ジョブ別ポイント / スキル値）。既定で開くのは
  基本情報とジョブレベルだけ。開閉状態は `localStorage['ff11sim_char_sections']` に保存する。
  畳んだ状態でも中身が分かるよう、`summary` に要約を出す
  （「基礎 135/135pt・スキル 264/264pt・その他 8/10pt」「上限 0 が 10 件」など）。
  サブグループはさらに畳まず、見出しで区切るだけにする。
- **アクションバー**: タイトル・未保存バッジ・保存・閉じるをフォーム上端に集約し
  `position: sticky` で固定する。最下部の `.btn-group` は削除する。
- **ジョブ選択の統合**: `jmJob` / `jpJob` を `targetJob` 1 つにまとめ、
  「ジョブ別ポイント」セクションの先頭に 1 つだけ置く。
- **クランプ**: 全数値欄で上限を超える入力を受け付けない。
  グループ合計に上限があるもの（ジョブ別メリット 各グループ 10、メリットその他 計 10）は
  「他項目の合計を引いた残り」で頭打ちにする。この 2 種のクランプは
  `web/src/character/limits.ts` の `clampToMax` / `clampWithinGroup` に集約する。
  メリットその他の合計上限は**既存コードに無かった制約**で、今回追加する
  （それまでは各欄 `max={5}` だけで合計 25 まで振れた）。
  上限の値は `web/src/constants.ts` に置き、根拠は
  [docs/knowledge/status/merit_points.md](../knowledge/status/merit_points.md) に記録する。
- **新規キャラクターのスキル上限を実態に合わせる**: 旧実装は新規作成時だけ
  `computeSkillDefaults()` をメリットポイント抜きで呼んでおり、
  フォームが既定で持つスキルメリット 8（上限 +16）が反映されず、
  表示上の「上限」が実際のキャップより 16 低かった。
  クランプを入れると本来入る値が弾かれるため、既定のメリットを含めて算出するよう直す。
- **読み込み時はクランプしない**: 保存済みの超過値はその欄を編集するまで残す。
  計算側は `effective_skill()` がジョブ由来のキャップで丸めるので実害が無く、
  読み込み直後に値を書き換えると `dirty` が即 true になって
  「未保存」表示が出てしまう（[ADR 0020](0020-unsaved-changes-guard.md)）。
- **上限 0 のスキル**: `disabled` にする。上限 0 とは
  `default_skill_value()` が返す「Lv1 以上のジョブのうち最大のキャップ」が 0、
  つまりどのジョブもそのスキルのランクを持たない状態
  （`job_skill_cap()` の `None => 0`）。ジョブレベルを上げれば自動で有効化される。
- **フォーカスで全選択**: 全数値欄に `onFocus={(e) => e.target.select()}` を付ける。

### Consequences

* Good: フォーム高さが 3,913px → 658px（既定の開閉状態）。全セクションを開いても 2,359px。
* Good: 広い画面では列数が増え、狭い画面では減る。3 列固定で余っていた横幅が使われる。
* Good: 各欄に分母が出るので、その欄に何を入れられるかがラベルを読まなくても分かる。
* Good: どれだけスクロールしても保存・閉じるが押せる。
* Good: グループ合計のクランプが 1 箇所（`clampWithinGroup`）になり、
  ジョブ別メリットとメリットその他で同じ規則が保証される。
* Bad: 既存編集で目的のセクションが畳まれていると 1 クリック増える。
  開閉状態を localStorage に持つことで、繰り返し同じ場所を触る場合には解消される。
* Bad: ジョブ選択を統合したので「戦士のメリットを見ながら侍の JP を編集する」ができなくなる。
* Bad: メリットその他に合計上限を入れたため、これまで合計 10 を超えて保存されていた
  データはその欄を触った時点で切り詰められる（読み込み時には変えない）。
* Bad: 新規キャラクターの初期スキル値が 16 上がる（メリット込みの上限で埋まるようになるため）。
  これまでが実際のキャップより低かったので実質は修正だが、
  新規作成した既存キャラクターと初期値が変わる。
* Bad: ジョブレベルのテーブルをやめたので列見出し（Lv / MLv）が消え、
  各チップ内の小さいラベルに頼ることになる。
* Neutral: スキル値の上限がジョブ由来であることは `title` 属性の説明に留めた。
  ジョブ別のキャップ内訳を出すには WASM に新しいエクスポートが要るため、今回は入れない。

### Confirmation

* `web/src/character/limits.test.ts`: `clampToMax` が範囲内をそのまま返す / 上限で丸める /
  負値と `NaN` を 0 にする / 上限 0 の項目は 0 しか通さないこと、
  `clampWithinGroup` が項目上限で止まる / 他項目の合計を引いた残りで頭打ちになる /
  残りが無ければ 0 になる / 自分自身の現在値を残りの計算に含めないことを検証する（10 件）。
* `tests/smoke.spec.js`「キャラクターを UI から作成できる」: `#charEditSection` の表示、
  `#charName` への入力、`#btnSaveChar` での保存、一覧と装備セットのキャラクター
  セレクタへの反映を確認する。セクションを `<details>` 化しても既定で
  「基本情報」が開いているため、この経路がそのまま通ることの回帰確認になる。
* `tests/smoke.spec.js`「保存済みキャラクターのステータスが 0 でなく表示される」:
  `localStorage` へ直接投入したキャラクターからステータスが算出されること。
  スキル値の保存形式を変えていないことの確認になる。
* `npm run typecheck`: `targetJob` への統合、`NumField` / `Section` の props、
  `SectionId` の網羅性を型で確認する。

## Pros and Cons of the Options

### 1.1. 列数固定のまま入力欄を狭める

* Good: CSS 1 行で済む
* Bad: セルの余白が増えるだけで、ラベルと入力が遠いままになる
* Bad: 3 列固定なので、広い画面の余りも狭い画面の溢れも解決しない

### 1.2. 列数を幅に追従させ、ラベルを同じ行に置く（採用）

* Good: 1 項目が 1 行になり、縦が約半分になる
* Good: 画面幅に対して列数が最適化される
* Bad: ラベルが長い項目（「被クリティカルヒット率」など）は `--col-min` を
  個別に指定しないと省略記号になる

### 2.1. 全セクション展開のまま

* Good: 全体像が常に見え、Ctrl+F で目的の欄に飛べる
* Bad: 密度改善後でも 2,359px あり、既存編集での移動量が大きいまま

### 2.2. サブタブに分割する

* Good: 装備セット画面と同じ操作感で、1 画面が確実に短くなる
* Bad: 全体像が見えず、どのタブに何があるかを覚える必要がある
* Bad: 畳んだ状態の要約に相当するものが出せない

### 2.3. `<details>` の開閉式（採用）

* Good: 畳んだ状態でも `summary` の要約で中身の状態が分かる
* Good: 既定の開閉状態を選べるので、新規作成の動線（基本情報 → ジョブレベル）が保てる
* Bad: 目的のセクションが畳まれていると 1 クリック増える
* Bad: 開閉状態を永続化しないと毎回畳まれた状態から始まるため、localStorage が要る

### 3.1. 7 セクションのまま

* Good: 変更が要らない
* Bad: 「メリットポイント」という同種の見出しが 3 つ並び、どれがどれか読み分けが要る

### 3.2. 5 セクションに束ねる（採用）

* Good: 畳んだときの一覧が 5 行になり、全体像が 1 画面に収まる
* Good: 同種のものが 1 つの親の下に集まり、`<h3>` が 3 本減る
* Bad: 親を開くと「メリットポイント (共通)」だけで 47 項目が一度に出る

### 4.1. ジョブセレクタを 2 つ維持する

* Good: ジョブ別メリットと JP で別々のジョブを見比べられる
* Bad: 同じセクションに同じ選択肢のセレクタが 2 つ並び、どちらが何に効くか分からない

### 4.2. 1 つに統合する（採用）

* Good: 「対象ジョブ」という 1 つの軸でセクション全体が決まる
* Good: 畳んだときの要約に「戦士 · G1 10/10 …」と 1 ジョブぶんを出せる
* Bad: 別々のジョブを同時に見る使い方ができなくなる（挙動の変更）

### 5.1. 超過を警告表示する

* Good: 装備・特性込みの値をあえて入れたい場合に妨げない
* Bad: 警告を無視した値は `effective_skill()` で丸められるので、
  画面の数字と計算結果が食い違ったままになる
* Bad: 「上限」を出しているのに超えられるのは、表示と挙動の不一致

### 5.2. 入力時にクランプする（採用）

* Good: 「上限」が「入力できる最大値」と一致し、分母表示の意味が確定する
* Good: 全ジョブ中の最大キャップでクランプするので、どのジョブで計算しても損しない
  （低いジョブでは `effective_skill()` がさらに丸める）
* Bad: 上限 0 のスキルが「0 しか入らない欄」になり、その見せ方を決める必要が出る（→ 6）

#### 5.2.1. 読み込み時にも一括クランプする

* Good: 保存データが常に上限内に保たれ、表示と保存内容が一致する
* Bad: 読み込んだだけで値が変わるため `dirty` が即 true になり、
  何もしていないのに「未保存」が出る（ADR 0020 と衝突する）

#### 5.2.2. 触るまで温存する（採用）

* Good: 読み込みが副作用を持たず、ADR 0020 の未保存判定と両立する
* Good: 計算側が丸めるので、温存しても結果に影響しない
* Bad: 保存データにしばらく上限外の値が残りうる

### 6.1. 上限 0 の欄を他と同じに表示する

* Good: 実装が要らない
* Bad: 触れるのに 0 しか入らず、なぜ入らないのか分からない

### 6.2. `disabled` にする（採用）

* Good: 一覧性を保ったまま、入力できないことがその場で分かる
* Good: ジョブレベルを上げれば自動で有効化される（状態を持たない）
* Bad: 該当ジョブを持たないキャラクターでは無効な欄が並ぶ
  （実キャラで 33 中 10 件程度。ただし新規作成時は全ジョブ Lv99 なので 0 件）

### 6.3. 畳んで別枠に出す

* Good: 一覧が短くなる
* Bad: なぜ消えたのかが分かりにくく、開くまで存在に気づけない

### 7.1. 何もしない

* Good: 標準的な挙動
* Bad: 既定値（99 や 15 や上限値）が入っている欄が大半なので、
  毎回消してから打ち直す手間がかかる

### 7.2. フォーカスで全選択する（採用）

* Good: クリックしてそのまま数字を打てば置き換わる
* Good: `onFocus={(e) => e.target.select()}` の 1 行で済む
* Good: 何も入力せずに欄を離れても元の値が残る
* Bad: 一部だけ直したい場合は選択を解除する操作が要る

### 7.3. フォーカスで中身を消す

* Good: 「空欄に打ち込む」という見た目になる
* Bad: 何も入力せずに離れると空になるため、元に戻す往復処理が要る。
  書かないと `parseNum('')` が 0 を返し、触っただけのジョブが Lv0 になって
  `withFollowedDefaults()` のスキル上限再計算まで巻き込む
* Bad: `skills` / `meritSkills` は `number` で保持しているので、
  入力途中の空文字を持たせるには `jobLevels` と同じく string 化が要る
